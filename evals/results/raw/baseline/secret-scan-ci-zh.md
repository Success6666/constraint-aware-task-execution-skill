# 密钥检测与例外审批方案

## 1. 目标与强制规则

### 目标

覆盖以下位置和流程：

- 本地提交前检查
- Pull Request 检查
- 主干和发布流水线检查
- 历史提交扫描
- 误报识别与例外审批
- 真实密钥泄露后的轮换和取证
- 自动化测试与持续验证

### 强制规则

1. 检测到未经批准的真实凭据时，CI 必须失败。
2. 例外只能通过仓库中的受保护配置审批，不能通过删除扫描结果、修改扫描器参数或跳过 CI 实现。
3. 例外不得包含原始密钥，只能包含不可逆指纹、位置和审批信息。
4. 例外必须限定范围、用途和有效期，默认最长 90 天。
5. 已确认泄露的真实凭据即使已经失效，也必须按泄露事件处理，并从代码和历史中清理。
6. 任何关闭检测规则、降低扫描级别或允许新增明文凭据的修改，都必须由安全负责人审批。

## 2. 检测分层

建议采用多引擎组合：

- `gitleaks`：高性能、适合提交和 PR 检查
- `detect-secrets`：基于插件的检测和基线管理
- `trufflehog`：对高熵凭据和历史提交进行深度扫描
- 自定义规则：公司内部 Token、云平台密钥、数据库连接串、私有证书等

所有引擎输出统一转换为内部结果格式：

```json
{
  "engine": "gitleaks",
  "rule_id": "aws-access-key",
  "repository": "org/repo",
  "commit": "abc123",
  "path": "config/example.env",
  "line": 12,
  "match_fingerprint": "sha256:...",
  "classification": "real|false_positive|test_fixture|unknown",
  "status": "open|approved_exception|revoked|resolved"
}
```

扫描结果必须保留：

- 规则 ID
- 仓库、分支、提交
- 文件路径和行号
- 不可逆匹配指纹
- 检测时间
- 分类状态
- 例外 ID或事件 ID

不得在日志、PR 评论、工件或告警中输出完整密钥。最多显示经过掩码处理的前后少量字符。

## 3. 本地检查

### 安装方式

为开发者提供统一入口：

```text
make secrets-install
make secrets-scan
make secrets-scan-staged
```

安装内容包括：

- pre-commit hook
- 固定版本的扫描器
- 仓库规则和配置
- 本地误报处理命令
- 与 CI 相同的规则包

扫描器版本、规则版本和配置必须锁定，避免开发者本地通过旧版本获得与 CI 不一致的结果。

### 提交前检查

pre-commit 只扫描：

- 暂存区文件
- 当前提交新增或修改的内容
- 与密钥相关的文件类型和差异

发现结果时阻止提交，并显示：

- 规则名称
- 文件和行号
- 风险等级
- 处理方式：删除、改用引用、提交例外申请或确认泄露事件

本地 hook 可以被临时跳过以完成紧急操作，但 CI 仍必须执行完整检查，因此跳过本地 hook 不构成绕过机制。

### 本地开发规则

禁止提交：

- 云访问密钥
- 数据库密码
- OAuth、JWT、API Token
- 私钥和证书私钥
- 包管理器、CI/CD、聊天机器人凭据
- 带密码的连接字符串
- 真实用户或生产环境测试凭据

允许提交：

- 文档中明确标记为无效的占位符，例如 `CHANGE_ME`
- 公开示例 Token，前提是经过确认且不可用于真实服务
- 测试专用假凭据，但必须使用统一的明显占位格式

推荐统一占位符：

```text
EXAMPLE_ONLY_NOT_A_SECRET
test-token-invalid
00000000-0000-0000-0000-000000000000
```

## 4. CI 流程

## 4.1 Pull Request 阶段

PR 必须执行以下检查：

1. 扫描 PR diff
2. 扫描 PR 涉及的文件
3. 扫描目标分支与 PR 合并结果
4. 检查所有结果是否有有效例外
5. 对疑似真实凭据执行安全验证
6. 检查例外文件是否被未经授权修改

建议流水线阶段：

```text
secret-detect-diff
secret-detect-merge
secret-validate-exceptions
secret-classify
security-gate
```

### CI 失败条件

以下任一情况必须失败：

- 检测到未知结果
- 结果被分类为 `real` 且没有有效例外
- 结果分类为 `unknown` 且无法证明是测试占位符
- 例外不存在、已过期、范围不匹配或审批人不足
- 例外配置格式错误
- 例外修改未通过安全审批
- 扫描器运行失败、规则文件缺失或无法获取完整历史
- 扫描被禁用或结果上传失败

扫描器自身失败不能被当作“无发现”处理，必须 fail closed。

## 4.2 主干和发布阶段

主干流水线必须额外执行：

- 全仓库当前状态扫描
- 默认分支全部历史提交扫描
- 生成版本和构建工件扫描
- 容器镜像、压缩包和生成文件扫描
- IaC、部署配置和环境模板扫描

发布阶段如果发现任何未经批准的真实凭据，必须阻止发布。

## 4.3 定期扫描

至少每天执行一次全历史扫描，扫描范围包括：

- 所有活跃分支
- 默认分支完整 Git 历史
- Tag 和 release 分支
- Git LFS 或其他大文件存储
- 构建产物和制品仓库中保留的源码包

定期扫描发现问题后创建安全事件，而不是只创建普通开发任务。

## 5. 真实凭据判定

检测结果分为三类：

### `real`

确认可用于真实服务，或来自真实环境配置的凭据。

判定依据可以包括：

- 使用服务方安全 API 进行只读、最小权限验证
- 与密钥管理系统或资产清单匹配
- 命中生产、预生产或共享环境凭据格式
- 由凭据所有者确认
- 具备真实账号、租户、项目或资源关联信息

验证请求必须：

- 使用只读或最小权限
- 不执行业务操作
- 不将密钥发送到第三方检测服务
- 不将密钥写入日志
- 在网络、审计和访问控制上受限

### `false_positive`

确认不是凭据，例如：

- 随机字符串
- 文档示例
- 哈希或签名样本
- 已被证明不可认证的字符串

必须有证据或明确规则支持，不能仅因为“看起来像测试数据”就归类为误报。

### `test_fixture`

仅限测试使用的假凭据，必须满足：

- 不关联任何真实服务
- 使用仓库规定的占位符
- 测试名称或目录能够清楚表达用途
- 不复用生产、预生产或个人凭据

无法确认时分类为 `unknown`，CI 按失败处理。

## 6. 例外审批机制

## 6.1 例外记录

例外配置只保存元数据和指纹：

```yaml
exceptions:
  - id: SEC-EX-2025-001
    fingerprint: sha256:...
    rule_id: generic-high-entropy
    repository: org/repo
    path: tests/fixtures/provider-response.json
    line_range: "20-20"
    classification: test_fixture
    reason: "第三方协议测试要求固定的无效 Token"
    owner: team-payments
    approver: security@example.com
    approved_at: "2025-01-15T10:00:00Z"
    expires_at: "2025-04-15T10:00:00Z"
    scope:
      branches:
        - main
      paths:
        - tests/fixtures/provider-response.json
    compensating_controls:
      - "服务端已确认该 Token 不可认证"
    review_ticket: SEC-1234
```

禁止记录：

- 原始密钥
- 完整匹配文本
- 可通过简单拼接恢复密钥的信息
- 生产账号、密码或 Token

## 6.2 审批要求

例外必须满足：

- 提交安全工单
- 由代码所有者和安全团队批准
- 对生产相关内容增加系统负责人批准
- 说明为什么必须保留
- 说明为什么不能改为占位符或安全注入
- 指定责任团队
- 指定过期时间
- 指定文件、行号、分支和规则范围

以下人员不得单独批准自己的例外：

- 例外提交者
- 凭据使用者
- 目标代码唯一维护者

审批配置必须使用受保护分支、CODEOWNERS 或等效的强制审批机制。CI 应通过 API 或签名元数据验证审批，而不是只检查 YAML 中是否存在 `approved: true`。

## 6.3 例外生命周期

- 默认有效期：30 天
- 最长有效期：90 天
- 到期前 14 天自动通知责任人
- 到期后自动使 CI 失败
- 延期必须重新说明原因并重新审批
- 无使用记录或对应内容删除后，例外应自动归档
- 每季度审计全部活跃例外

例外只允许匹配原位置和原指纹。密钥内容、路径、规则或分支变化后，必须重新审批。

## 7. 误报处理流程

### 普通误报

1. 开发者提交例外申请。
2. 安全人员确认字符串不具备认证能力。
3. 生成不可逆指纹。
4. 将例外限制到具体文件、行和规则。
5. 通过受保护审批后合并。

### 可直接修复的误报

优先修改代码：

- 使用标准占位符
- 将文档样例改为明确无效值
- 将固定数据移入测试生成器
- 使用动态 mock，而非固定高熵字符串
- 将示例配置改为环境变量引用

### 不允许的误报处理

以下方式不得接受：

- 全局加入目录白名单
- 禁用高熵检测
- 添加宽泛正则排除
- 以整个文件或整个仓库为例外范围
- 只依赖文件名判断为测试文件
- 在检测结果中直接标记为安全而无审批记录

## 8. 发现真实凭据后的响应和轮换

一旦发现疑似真实凭据，应按泄露事件处理，不等待 PR 合并。

### 立即操作

1. 立即阻断合并和发布。
2. 创建安全事件并记录提交、分支、路径和发现时间。
3. 判断凭据类型、权限、环境和资产所有者。
4. 通过凭据提供商或密钥管理系统吊销、禁用或轮换。
5. 检查访问日志，确认是否被使用。
6. 评估横向影响，例如同一账号的其他 Token 或共享密码。
7. 从当前代码、构建产物和配置中移除凭据。
8. 必要时清理 Git 历史和制品仓库。
9. 重新扫描所有分支、Tag、镜像和缓存。
10. 由安全负责人关闭事件。

### 轮换要求

轮换必须优先在服务端完成，不能只修改仓库中的字符串。

按凭据类型定义轮换 SLA：

- 生产高权限凭据：发现后立即吊销，目标在 15 分钟内完成
- 生产低权限凭据：目标在 1 小时内完成
- 预生产或开发凭据：目标在 1 个工作日内完成
- 无法确认权限的凭据：按高权限处理

轮换后必须验证：

- 新凭据通过密钥管理系统注入
- 旧凭据不可用
- CI、部署和运行时均使用新凭据
- 审计日志没有继续出现旧指纹
- 旧凭据未残留在 Git 历史、缓存、制品或日志中

如果因审计需要保留历史提交，不应把历史内容简单标为例外；应先完成吊销和风险评估，再决定是否使用受控历史重写。

## 9. 正确的密钥使用方式

代码中只允许引用密钥名称或环境变量：

```text
PAYMENT_API_TOKEN=${secretManager://payments/api-token}
DATABASE_PASSWORD=${secretManager://orders/database-password}
```

推荐注入方式：

- CI 使用 OIDC 获取短期凭据
- 部署平台从密钥管理系统注入环境变量或文件
- 应用运行时使用云平台 Workload Identity
- 开发环境使用个人密钥链或本地密钥管理器
- 禁止将共享长期 Token 放入 `.env` 并提交仓库

密钥生命周期应尽量短，权限遵循最小权限，生产和非生产环境必须隔离。

## 10. 测试策略

## 10.1 检测器单元测试

每条自定义规则至少包含：

- 正向真实样例
- 掩码样例
- 明确无效占位符
- 边界长度
- 前后空白和编码变化
- JSON、YAML、Shell、Terraform、Dockerfile 等常见格式
- 误报样例

真实样例必须是不可认证、专门用于测试的合成数据，不能使用任何生产凭据。

## 10.2 CI 集成测试

建立独立的安全流水线测试仓库或临时测试分支，验证：

- 新增未批准凭据时 CI 失败
- 只修改普通代码时 CI 通过
- 有效例外匹配时 CI 通过
- 过期例外时 CI 失败
- 路径或分支超出例外范围时 CI 失败
- 指纹变化时 CI 失败
- 例外文件未经过规定审批时 CI 失败
- 扫描器异常退出时 CI 失败
- 历史提交中的凭据可以被发现
- 生成的日志不会泄露完整密钥
- 多扫描器重复结果可以正确去重

## 10.3 轮换流程测试

使用专门的测试账户定期验证：

- 检测到测试凭据后能创建事件
- 自动或人工轮换流程可执行
- 旧凭据被吊销
- 新凭据能被应用和 CI 使用
- 轮换后扫描不再报旧凭据
- 审计记录包含责任人、时间和结果

## 10.4 定期回归

每次升级扫描器、规则或 CI 模板时必须运行：

- 全部规则回归测试
- 历史样本扫描
- 例外匹配测试
- 性能测试
- 日志脱敏测试

规则包和扫描器升级应通过版本控制和变更审批发布。

## 11. 责任与告警

角色划分：

- 开发者：修复发现、提交例外申请
- 代码所有者：确认业务必要性
- 安全团队：确认风险、批准例外、处理事件
- 平台团队：维护 CI、扫描器和密钥注入
- 服务所有者：执行凭据吊销和轮换
- 审计负责人：定期检查例外、事件和扫描覆盖率

告警必须发送到：

- PR 检查
- 安全事件系统
- 责任团队
- 安全值班渠道

高风险凭据告警应立即通知，不应等待每日汇总。

---

## 12. 验收标准

方案上线后必须满足：

- 任意 PR 中新增未经批准的真实凭据都会阻止合并。
- 任何主干或发布任务发现未经批准的真实凭据都会失败。
- 扫描器异常、配置缺失和结果上传失败都会失败。
- 例外不包含原始密钥，且必须有责任人、审批人、范围和过期时间。
- 过期或范围不匹配的例外不会绕过 CI。
- 本地提交前可以发现常见凭据。
- 默认分支完整历史至少每日扫描一次。
- 真实凭据发现后有可审计的吊销、轮换和影响评估记录。
- 测试覆盖正向检测、误报、例外、过期、范围限制、日志脱敏和轮换流程。
- 安全团队能够查询当前所有开放发现、有效例外和待轮换凭据。
