# 模块化单体计费系统设计

采用单体部署、单一进程和单一数据库集群，但在代码、数据和事务上严格划分模块。模块之间通过明确的应用接口和进程内事件通信，禁止直接访问其他模块的内部类或表。

## 一、模块划分

### 1. 订阅模块（Subscription）

负责客户与计费计划之间的商业关系：

- 产品、价格方案、计费周期
- 订阅创建、升级、降级、暂停、取消
- 生效时间、试用期、按比例计费策略
- 订阅状态：`trialing`、`active`、`past_due`、`paused`、`canceled`
- 订阅变更历史

核心实体：

- `Customer`
- `Plan`
- `Price`
- `Subscription`
- `SubscriptionChange`

对外提供：

```text
createSubscription()
changePlan()
cancelSubscription()
pauseSubscription()
getEffectiveSubscription(at)
```

订阅模块不负责计算用量金额，也不负责扣款。

---

### 2. 计量模块（Metering）

负责记录和汇总客户的资源使用量：

- 接收使用事件，例如 API 调用数、存储量、席位数
- 事件去重和幂等
- 按客户、资源、时间窗口聚合
- 提供账单周期内的用量快照
- 修正、撤销或补录用量

核心实体：

- `UsageEvent`
- `UsageAggregate`
- `UsageCorrection`
- `MeterDefinition`

对外提供：

```text
recordUsage()
getUsageSnapshot(customerId, period)
rebuildUsage()
```

计量模块只记录“用了多少”，不决定“收多少钱”。价格规则由订阅模块提供，金额计算由账单模块完成。

---

### 3. 账单模块（Billing）

负责将订阅费用和用量转换成应收账单：

- 开账单周期
- 读取订阅有效价格
- 获取计量模块的用量快照
- 计算固定费、阶梯价、按量价、折扣、税费
- 生成账单、账单明细和贷项通知单
- 账单确认、作废、重算
- 应收余额和账龄

核心实体：

- `BillingPeriod`
- `Invoice`
- `InvoiceLine`
- `CreditNote`
- `AccountBalance`

账单状态：

```text
draft -> finalized -> payable -> paid
                         -> overdue
draft -> void
```

对外提供：

```text
previewInvoice()
generateInvoice()
finalizeInvoice()
voidInvoice()
getOutstandingBalance()
```

账单生成时必须保存价格、折扣和用量快照，不能只保存外部 ID，否则未来修改计划或价格会导致历史账单变化。

---

### 4. 支付模块（Payment）

负责支付工具、支付尝试和支付结果：

- 支付方式令牌化引用
- 创建支付订单或支付意图
- 发起扣款、重试和退款
- 接收支付渠道回调
- 支付状态对账
- 支付失败策略和催收状态

核心实体：

- `PaymentMethod`
- `PaymentAttempt`
- `Payment`
- `Refund`
- `PaymentProviderEvent`

支付模块不修改账单金额，也不直接修改订阅状态。它通过账单模块的应用接口报告支付结果，由账单模块更新应收状态，再由订阅模块根据账单结果决定是否进入 `past_due` 或暂停。

---

## 二、模块边界与依赖

建议依赖方向：

```text
订阅模块 ─────┐
              ├──> 账单模块 ───> 支付模块
计量模块 ─────┘
```

实际代码中应避免形成循环依赖：

- 订阅模块可发布 `SubscriptionActivated`、`SubscriptionChanged`
- 计量模块可发布 `UsagePeriodClosed`
- 账单模块订阅这些事件并生成账单
- 支付模块发布 `PaymentSucceeded`、`PaymentFailed`
- 账单模块消费支付事件并更新账单
- 订阅模块消费 `InvoiceOverdue`，执行暂停或催收策略

事件只携带稳定的业务数据，例如：

```json
{
  "eventId": "evt-123",
  "customerId": "cus-1",
  "subscriptionId": "sub-1",
  "occurredAt": "2026-08-22T10:00:00Z"
}
```

跨模块引用使用 ID 或公开 DTO，不暴露内部实体、ORM 模型和仓储。

## 三、数据库设计

仍使用一个数据库，但按模块隔离表和权限：

```text
subscription_* 
metering_*
billing_*
payment_*
```

推荐规则：

- 每个模块只能通过自己的仓储访问自己的表。
- 禁止跨模块 SQL Join。
- 跨模块查询通过应用服务组合结果。
- 共享内容仅限基础类型、货币、时间、租户上下文和错误码。
- 不建立跨模块外键，避免数据库层耦合。
- 可为每个模块配置独立数据库用户权限，即使物理上仍是同一个数据库。

## 四、事务设计

### 1. 单模块强一致事务

以下操作在一个本地数据库事务内完成：

- 创建订阅及订阅变更记录
- 写入用量事件及幂等键
- 生成账单及账单明细
- 记录支付尝试及状态变化
- 账单状态和余额更新

例如生成账单：

```text
BEGIN
  锁定 billing_period
  读取订阅有效配置
  获取用量快照
  计算金额
  写入 invoice 和 invoice_line
  标记 billing_period 已生成
COMMIT
```

账单生成必须使用唯一约束：

```text
UNIQUE(customer_id, billing_period_id)
```

确保重复执行不会产生重复账单。

### 2. 跨模块流程不使用分布式事务

模块间流程采用：

- 本地事务
- 事务内写入 `outbox_event`
- 事务提交后由进程内事件发布器投递
- 消费方使用 `inbox_event` 或业务幂等键去重
- 失败后重试，必要时进入死信表

例如自动扣款：

```text
账单 finalized
  -> 发布 InvoiceFinalized
  -> 支付模块创建 PaymentAttempt
  -> 支付成功，发布 PaymentSucceeded
  -> 账单模块标记 paid
  -> 发布 InvoicePaid
  -> 订阅模块清除 past_due 状态
```

即使事件重复投递，处理结果也必须一致。

### 3. 并发控制

- 账单周期使用乐观锁或行锁，防止并发开票。
- 用量写入使用幂等事件 ID。
- 支付回调按支付渠道事件 ID 去重。
- 账单状态采用显式状态机，禁止任意状态更新。
- 金额使用定点十进制，不使用浮点数。
- 所有金额计算明确舍入规则和货币精度。

## 五、典型业务流程

### 订阅开通

1. 订阅模块校验客户和价格。
2. 创建订阅，提交事务。
3. 发布 `SubscriptionActivated`。
4. 账单模块按策略生成首期账单。
5. 支付模块发起扣款。
6. 根据支付结果更新账单和订阅状态。

### 周期结算

1. 定时任务扫描到期的 `BillingPeriod`。
2. 计量模块冻结并生成用量快照。
3. 账单模块读取订阅和快照，生成账单。
4. 账单最终化后触发支付。
5. 支付成功则标记已支付，失败则进入重试和催收流程。

### 计划变更

1. 订阅模块记录变更及生效时间。
2. 根据策略生成按比例调整项。
3. 账单模块将调整项写入当前或下一期账单。
4. 不修改已最终化账单，必要时生成贷项或补充账单。

## 六、测试策略

### 单元测试

每个模块独立测试领域规则：

- 订阅状态转换和生效时间
- 计量去重、聚合、修正
- 阶梯价格、折扣、税费和舍入
- 账单状态机
- 支付重试、退款和回调映射

金额计算应覆盖边界值、零用量、跨周期、负调整和货币精度。

### 模块应用服务测试

使用模块自己的测试数据库或内存替身，验证：

- 输入校验
- 权限和租户隔离
- 仓储调用
- 事务提交和回滚
- 幂等行为
- 事件是否正确写入 outbox

### 模块契约测试

针对公开接口和事件建立契约测试：

- 事件字段、版本和兼容性
- 账单模块对订阅、计量接口的依赖
- 支付回调到支付结果事件的映射
- 禁止暴露内部实体和数据库模型

### 集成测试

使用真实数据库和支付网关沙箱，覆盖：

- 订阅开通到首账单
- 用量结算到最终账单
- 支付成功、失败、重试、重复回调
- 计划升级、降级、取消
- 事务回滚和 outbox 重试

### 端到端测试

至少覆盖以下主链路：

```text
创建客户
-> 创建订阅
-> 上报用量
-> 生成账单
-> 发起支付
-> 接收支付回调
-> 查询余额和订阅状态
```

### 数据与可靠性测试

- 重复请求和重复事件测试
- 并发开票测试
- 事件乱序测试
- 数据库故障恢复测试
- outbox/inbox 堆积和重放测试
- 账单重算结果与历史账单不可变性测试

## 七、工程约束

建议每个模块采用统一目录：

```text
subscription/
  domain/
  application/
  infrastructure/
  api/

metering/
billing/
payment/
```

代码评审重点检查：

- 是否越过模块接口访问数据
- 是否把跨模块逻辑塞进共享工具类
- 是否缺少幂等键和状态机校验
- 是否在事务中调用外部支付接口
- 是否允许历史账单被重新计算
- 是否把模块化单体不必要地演化成微服务边界

这样可以在保持单体部署和运维简单的同时，获得清晰的领域边界、可控的一致性和可独立演进的代码结构。
