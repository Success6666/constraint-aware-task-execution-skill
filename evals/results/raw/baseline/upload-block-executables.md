## Architecture

Use three components:

1. **API service**
   - Authentication, authorization, upload sessions, metadata, downloads, and audit events.
2. **Relational database**
   - File metadata, upload state, scan results, ownership, retention, and audit records.
3. **Durable object storage**
   - Versioning enabled, server-side encryption enabled, private buckets, replicated across availability zones or regions.

Use separate storage areas:

- `quarantine`: newly uploaded objects, never downloadable
- `accepted`: objects that passed validation and scanning
- `rejected`: optional short-lived retention for investigation, otherwise delete

Object keys must be generated by the service, for example:

```text
{tenant-id}/{file-id}/{content-sha256}
```

Never use the client-provided filename as a storage path.

## API

### Create upload

```http
POST /v1/files
Authorization: Bearer ...
Content-Type: application/json
```

Request:

```json
{
  "filename": "report.pdf",
  "declared_content_type": "application/pdf",
  "size": 184392
}
```

Response:

```http
201 Created
```

```json
{
  "file_id": "01J...",
  "upload_url": "https://storage.example/...",
  "expires_at": "2026-01-01T12:00:00Z",
  "status": "pending"
}
```

The service should enforce:

- authenticated tenant ownership
- maximum file size
- allowed filename length and Unicode normalization
- no path separators or control characters
- upload expiration
- optional tenant-specific quotas

For large files, use multipart or resumable uploads. The client must not be able to mark an upload as complete without server-side validation.

### Complete upload

```http
POST /v1/files/{file_id}/complete
Authorization: Bearer ...
```

Response:

```http
202 Accepted
```

```json
{
  "file_id": "01J...",
  "status": "scanning"
}
```

The service verifies the object exists, its actual size matches limits, and its checksum matches the uploaded content if a checksum was supplied.

### Get metadata

```http
GET /v1/files/{file_id}
Authorization: Bearer ...
```

Response:

```json
{
  "file_id": "01J...",
  "filename": "report.pdf",
  "status": "available",
  "size": 184392,
  "detected_content_type": "application/pdf",
  "sha256": "...",
  "created_at": "2026-01-01T12:00:00Z",
  "created_by": "user-123"
}
```

Do not expose storage keys, scanner internals, bucket names, or arbitrary client-supplied metadata.

Possible states:

```text
pending
scanning
available
rejected
deleted
expired
```

### Download

```http
GET /v1/files/{file_id}/content
Authorization: Bearer ...
```

Only `available` files can be downloaded. The service must authorize access before returning a stream or issuing a short-lived signed URL.

Response headers:

```http
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="report.pdf"
X-Content-Type-Options: nosniff
Cache-Control: private, no-store
```

Use the sanitized original filename only for display. Never reflect it into an executable path or HTML context. Download access must support range requests only if authorization is checked for the entire request.

## Upload validation and executable rejection

The client-provided extension and MIME type are untrusted hints. They must not determine acceptance.

The scanner pipeline should:

1. Read the object from quarantine.
2. Enforce actual byte-size limits.
3. Compute SHA-256.
4. Detect the actual format using a trusted file-type library and format parsers.
5. Compare detected type against the declared MIME type and extension.
6. Scan for malware using an antivirus engine and, where appropriate, YARA rules.
7. Recursively inspect archives.
8. Reject executable or ambiguous content.
9. Promote the object to accepted storage only after all checks pass.

The policy should reject at minimum:

- Windows PE files, including `.exe`, DLLs, drivers, and PE files with misleading extensions
- ELF binaries
- Mach-O binaries and universal binaries
- scripts identified by shebang, such as shell, Python, Ruby, Perl, and Node scripts
- Windows batch, command, PowerShell, VBScript, and JScript files
- WebAssembly modules if they are not explicitly required
- executable installers and binary container formats
- archives containing any executable or script member
- encrypted archives, unless they can be safely inspected
- malformed or ambiguous polyglot files
- documents containing executable macros or embedded active content, unless explicitly allowed and sanitized

Detection must inspect both:

- magic bytes and structural headers
- parsed internal structures, not only the first few bytes

Examples that must be rejected:

- `invoice.pdf` containing a PE executable
- `photo.jpg` with `Content-Type: image/jpeg` but an ELF header
- a shell script named `notes.txt`
- a ZIP named `.docx` containing an executable
- a valid PDF with an embedded executable attachment or active macro-like payload

If any detector identifies executable content, or detectors disagree about the format, reject the upload. Scanner failures, timeouts, unsupported formats, archive traversal limits, and decompression limits must fail closed.

Recommended limits include:

- maximum uncompressed archive size
- maximum compression ratio
- maximum archive nesting depth
- maximum number of archive entries
- maximum scan duration
- maximum parsed object size

Do not rely solely on extension/MIME mismatch rejection. A matching extension and MIME type must still be scanned by content.

A successful scan should record:

```json
{
  "sha256": "...",
  "detected_type": "application/pdf",
  "scanner_verdict": "clean",
  "scanner_version": "2026.01",
  "checked_at": "2026-01-01T12:01:00Z"
}
```

Promotion from quarantine to accepted storage must be atomic from the API’s perspective. Metadata should become `available` only after promotion succeeds.

## Metadata model

A file record should contain:

```text
file_id
tenant_id
owner_id
original_filename
sanitized_filename
declared_content_type
detected_content_type
size_bytes
sha256
storage_version_id
status
rejection_code
scan_verdict
scanner_version
created_at
completed_at
deleted_at
retention_until
```

Store the original filename as data only. Normalize it for display and remove control characters, path components, and dangerous bidirectional characters.

Use content hashes for deduplication only within an authorization boundary. Do not allow one tenant to infer another tenant’s files from hash existence.

## Audit logging

Create append-only audit events for:

- upload initiated
- upload completed
- scan started
- scan passed
- scan rejected
- metadata viewed
- download authorized
- download denied
- file deleted
- retention changed
- administrative access

Each event should include:

```text
event_id
tenant_id
actor_id
action
file_id
timestamp
request_id
source_ip
user_agent
result
reason_code
metadata_snapshot
```

Audit records should be append-only, access-controlled, retained according to policy, and exported to immutable or WORM-capable storage. Avoid recording file contents, access tokens, or unnecessary personal data. A hash chain or tamper-evident log export is appropriate for higher assurance.

## Security controls

- TLS for all API and storage traffic
- encryption at rest with managed keys
- private object storage with no public ACLs
- least-privilege service identities
- tenant-scoped authorization on every endpoint
- rate limiting and quota enforcement
- request IDs propagated into audit records
- malware scanner isolation and resource limits
- no server-side execution of uploaded content
- no user-controlled redirects
- no inline rendering by default
- object storage versioning and lifecycle policies
- retention-based deletion with an auditable deletion event
- periodic re-scanning when scanner signatures or policy rules change

## Transaction and failure behavior

Use an outbox or equivalent reliable event mechanism for asynchronous scan jobs.

Required behavior:

- database creation succeeds but storage upload fails: mark the upload expired or failed
- storage upload succeeds but completion fails: leave it quarantined and clean it up later
- scanner unavailable: keep status `scanning`; do not expose the object
- scan rejects: mark `rejected`, record a stable reason code, and prevent downloads
- accepted-object promotion fails: keep the file unavailable and retry safely
- repeated completion requests: idempotent
- repeated delete requests: idempotent
- download after deletion or rejection: return `404` or `410` according to the API contract, without revealing sensitive state

Use stable error responses such as:

```text
FILE_TOO_LARGE
UNSUPPORTED_TYPE
EXECUTABLE_CONTENT
MALWARE_DETECTED
ARCHIVE_UNSAFE
CONTENT_AMBIGUOUS
SCAN_UNAVAILABLE
FILE_NOT_AVAILABLE
```

Do not return detailed scanner findings to untrusted clients.

## Verification and tests

### Unit tests

Test:

- filename normalization
- extension and MIME mismatch handling
- PE, ELF, Mach-O, script, and WebAssembly detection
- shebang detection
- archive recursion
- encrypted archive rejection
- zip bomb and decompression limits
- macro or embedded executable detection
- polyglot and malformed-file rejection
- checksum and size validation
- state transitions
- idempotent completion and deletion
- authorization checks
- safe `Content-Disposition` generation

### Integration tests

Use real or containerized object storage and scanner services to verify:

- uploads remain inaccessible during scanning
- clean files are promoted and downloadable
- rejected files cannot be downloaded
- misleading MIME types and extensions do not bypass scanning
- scanner timeout and outage fail closed
- retries do not duplicate metadata or audit events
- object storage failures leave consistent database state
- tenant isolation
- range downloads remain authorized
- audit events are emitted for success and denial paths

### Required security fixtures

Include actual samples or generated fixtures for:

```text
valid PDF renamed to .jpg
PE executable renamed to .pdf
ELF executable with image/jpeg
Mach-O executable with text/plain
shell script renamed to .txt
PowerShell script renamed to .docx
ZIP containing an executable
nested archive containing a script
encrypted ZIP
polyglot file
malformed file with conflicting format signatures
PDF with embedded executable content
```

### End-to-end acceptance criteria

The implementation is complete when:

- no uploaded object is downloadable before a clean verdict
- executable content is rejected based on bytes and structure, regardless of extension or MIME
- archive-contained executables are rejected
- scanner failures do not produce an available file
- accepted files survive service restarts and storage-node failures
- metadata and audit records remain consistent with object state
- every download is authorized and auditable
- automated tests cover all required fixtures and failure paths
- metrics and alerts exist for rejected uploads, scanner failures, quarantine backlog, and promotion failures
