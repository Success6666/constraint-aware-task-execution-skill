# 支付重试服务测试方案

## 1. 测试目标

验证支付重试服务能够：

- 正确处理支付成功；
- 区分瞬时失败与永久失败；
- 按配置执行重试次数和退避策略；
- 保证请求、消息、回调重复时不重复扣款；
- 在服务重启、并发和回调竞态下保持状态一致；
- 提供完整的日志、指标和链路追踪。

## 2. 无 Mock 测试环境

禁止使用 mock、stub 或仅验证调用次数的替身，使用以下真实依赖：

- 支付服务商 Sandbox；
- 独立测试数据库；
- 独立消息队列或任务调度器；
- 真实 HTTP/TLS、签名校验和回调链路；
- 测试环境故障注入代理，用于真实注入超时、断连、503、429 等网络或协议故障；
- 测试时钟、短周期调度配置或可暂停的测试调度器。

执行前固定记录：

- 最大重试次数 `N`；
- 基础延迟 `D`；
- 退避算法；
- 最大延迟 `M`；
- 抖动范围；
- 可重试错误码；
- 幂等键生成与唯一约束规则。

## 3. 核心场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| S01 | 首次支付成功 | 订单进入 `PAID`，仅产生一笔成功支付，无重试任务 |
| S02 | 首次超时，第二次成功 | 第一次记录为可重试失败，按退避等待，第二次成功，不能重复扣款 |
| S03 | 连续瞬时失败 | 恰好执行 `N` 次，达到上限后进入耗尽或人工介入状态，不再排队 |
| S04 | 永久失败 | 只执行一次，立即进入失败终态，不生成重试任务 |
| S05 | 错误分类边界 | 408、429、5xx、连接超时等按策略重试；余额不足、卡过期、参数非法等不重试 |
| S06 | 指数退避 | 第 k 次执行时间符合配置公式，不能早于最小延迟，也不能超过最大延迟 |
| S07 | 服务重启恢复 | 已落库的待重试任务不丢失、不重复执行，服务恢复后继续处理 |
| S08 | 相同幂等键重复提交 | 返回同一结果或处理中状态，不新增支付尝试 |
| S09 | 不同幂等键提交同一订单 | 按业务契约拒绝冲突或只允许一个成功，不得双重扣款 |
| S10 | 回调与重试竞态 | 回调和重试同时到达时，最终只保留一个成功结果，迟到失败不能覆盖成功 |
| S11 | 消息重复投递 | 同一消息重复消费不会产生第二次渠道请求 |
| S12 | 配置边界 | `N=0`、`N=1`、最大延迟、已终态订单等边界行为符合约定 |

## 4. 重点测试步骤

### 4.1 成功路径

1. 创建唯一测试订单和幂等键。
2. 通过真实支付 Sandbox 发起支付。
3. 等待同步响应和真实回调。
4. 查询订单、支付尝试、渠道流水号和队列。

断言：

- 状态只按合法状态机迁移到 `PAID`；
- 金额、币种和渠道流水号一致；
- 支付尝试数为 1；
- 队列中不存在重试任务；
- 渠道侧只有一笔成功交易。

### 4.2 瞬时失败与恢复

1. 对指定幂等键注入真实连接超时或 503。
2. 记录第一次失败时间 `t0`、尝试序号和下一次调度时间 `tn`。
3. 等待或推进测试调度器。
4. 恢复 Sandbox 响应为成功。
5. 查询支付记录和渠道交易列表。

断言：

- 错误被标记为可重试；
- `tn - t0` 满足退避公式、上下限及抖动范围；
- 第二次请求成功后订单进入 `PAID`；
- 失败尝试不会导致重复扣款；
- 最终只有一笔成功渠道交易。

### 4.3 永久失败

1. 使用 Sandbox 的余额不足、卡过期或参数非法场景。
2. 等待响应和状态落库。
3. 检查队列及支付尝试记录。

断言：

- 只执行一次；
- 订单立即进入失败终态；
- 不生成重试任务；
- 用户错误信息可识别，但不泄露渠道凭据或敏感卡信息。

### 4.4 达到重试上限

1. 连续注入可重试错误。
2. 按调度时间执行到第 `N` 次。
3. 检查状态、队列、死信和告警。

断言：

- 执行次数严格等于 `N`；
- 第 `N` 次之后不再生成任务；
- 进入耗尽或人工介入状态；
- 告警包含订单号、幂等键、最后错误和 trace ID。

### 4.5 幂等性和并发

1. 对同一幂等键并发发送多个真实请求。
2. 分别在“处理中”和“已成功”阶段重复提交。
3. 重复投递同一回调和同一重试消息。
4. 使用不同幂等键并发提交同一订单。

断言：

- 数据库唯一约束和业务锁共同生效；
- 重复请求返回稳定结果；
- 回调可重复消费；
- 同一订单最多产生一笔成功支付；
- 任何时序下都不能重复扣款。

## 5. 数据与清理

每个用例使用唯一：

- `order_id`；
- `payment_id`；
- 幂等键；
- 测试商户或 Sandbox 账户。

保存以下证据：

- 订单状态变化；
- 支付尝试时间线；
- 渠道流水号；
- 队列投递与确认记录；
- 数据库快照；
- 日志、指标和 trace。

测试结束后清理测试订单、队列消息、回调记录和观测数据。失败用例保留证据并登记责任人。

## 6. 可观测性与安全检查

必须能够按幂等键和 trace ID 查询：

- 每次支付尝试；
- 错误分类；
- 下一次重试时间；
- 最终状态；
- 渠道流水号。

至少检查以下指标：

- 重试率；
- 永久失败率；
- 重试耗尽率；
- 各错误类型失败率；
- 实际退避延迟；
- 重复请求拦截次数。

安全检查：

- 日志不得输出完整卡号、签名或支付凭据；
- 回调验签失败不得改变订单状态；
- 金额、币种和订单号必须服务端校验；
- 错误响应不得泄露渠道内部凭据。

## 7. 执行顺序

1. 快速回归：S01、S04、S08、S11。
2. 集成测试：S02、S03、S05、S06、S07、S09、S10、S12。
3. 发布前测试：服务重启、并发竞态、重复回调、消息重复投递和故障组合。
4. 所有测试必须使用真实 API、数据库和消息队列客户端。

## 8. 通过标准

- 成功、瞬时失败、永久失败、退避、幂等性五类场景全部通过；
- 无重复扣款；
- 无超过最大次数的重试；
- 无提前重试或终态回退；
- 服务重启后任务可恢复；
- 高危安全问题为 0；
- 所有失败均能通过日志、指标、trace 和数据库记录定位；
- 测试数据和 Sandbox 交易均完成清理。
