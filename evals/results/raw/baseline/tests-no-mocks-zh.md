**支付重试服务测试方案**

**一、测试目标与边界**

验证以下行为：

- 支付成功后只产生一次成功结果。
- 瞬时失败按策略重试，并最终成功或耗尽次数。
- 永久失败不重试，或只执行业务明确允许的有限补偿流程。
- 重试间隔符合退避策略，并包含随机抖动时的边界约束。
- 同一业务请求、同一重试任务、重复回调都不会导致重复扣款或状态回退。
- 服务重启、超时、网络中断、重复投递等情况下，支付状态最终一致。

测试使用真实数据库、真实消息队列和可执行的支付网关测试端点。支付网关使用测试服务器或沙箱，通过 HTTP 响应、连接断开和延迟来控制结果，不使用 mock 对象。

**二、可测试的系统设计**

1. 支付请求必须带有稳定的 `idempotency_key`，通常由商户号、订单号和支付意图版本组成。
2. 数据库保存：
   - 支付意图：`payment_id`、`order_id`、金额、当前状态。
   - 网关请求记录：`attempt_id`、`idempotency_key`、请求次数、网关响应、开始和结束时间。
   - 重试任务：下一次执行时间、已执行次数、退避时间、任务状态。
3. 为支付状态定义单向状态机，例如：
   - `PENDING -> PROCESSING`
   - `PROCESSING -> SUCCEEDED`
   - `PROCESSING -> RETRY_WAITING`
   - `PROCESSING -> FAILED_PERMANENTLY`
   - `PROCESSING -> UNKNOWN`
   - `UNKNOWN -> SUCCEEDED | FAILED_PERMANENTLY`
4. 对网络超时或连接断开这类“结果未知”的情况，不能直接判定为失败并重新扣款；必须先通过相同幂等键查询网关结果。
5. 将时钟、重试调度和网关测试端点配置为可替换的运行时组件。测试中使用可控时钟和测试调度器，不通过 sleep 等待真实时间。

**三、测试环境**

- 独立测试数据库，执行真实事务、唯一约束和行锁。
- 独立测试消息队列，支持重复投递和至少一次消费。
- 支付网关测试服务器，提供以下可配置行为：
  - 返回指定 HTTP 状态和业务错误码。
  - 延迟响应后返回成功。
  - 建立连接后直接断开。
  - 同一幂等键重复请求时返回首次请求的最终结果。
  - 支持按请求序号配置结果，例如第一次超时、第二次返回限流、第三次成功。
- 可控时钟：通过推进时间触发到期重试。
- 测试数据在每个场景开始前创建，在结束后清理或使用隔离数据库。

**四、核心测试场景**

### 1. 成功路径

| 场景 | 操作 | 预期 |
|---|---|---|
| 首次成功 | 创建支付并调用服务 | 只发送一次网关请求，状态为 `SUCCEEDED` |
| 成功响应重复消费 | 重复投递同一支付消息 | 不新增扣款请求，状态不变 |
| 已成功支付再次发起 | 使用相同幂等键再次请求 | 返回原成功结果，不重复扣款 |
| 成功后重复回调 | 网关发送多次成功通知 | 只处理一次，订单只完成一次 |
| 成功后重试任务到期 | 已成功记录但旧任务仍被执行 | 任务被跳过，不发送网关请求 |

断言数据库中的支付记录、网关请求记录、订单状态和发布的领域事件均只出现一次有效成功结果。

### 2. 瞬时失败

瞬时失败至少覆盖：

- HTTP `408`、`429`、`500`、`502`、`503`、`504`。
- 连接重置、DNS/连接失败、响应读取超时。
- 网关明确返回“稍后重试”的业务错误码。
- 第一次或前几次失败，后续成功。

典型场景：

1. 第一次返回 `503`，第二次成功：任务进入等待状态，时间到期后重试，最终成功。
2. 连续三次返回 `503`：达到最大尝试次数后进入 `FAILED_PERMANENTLY` 或人工处理状态。
3. 第一次 `429`：读取 `Retry-After`，若系统设计支持，则使用不早于该值的下一次执行时间。
4. 请求超时但网关已受理：服务进入 `UNKNOWN`，使用相同幂等键查询；查询结果为成功时不得再次扣款。
5. 请求超时且网关未受理：查询确认不存在后才允许重试。

每个场景都要断言：重试次数、任务状态、下一次执行时间、最终支付状态、网关实际受理次数和订单状态。

### 3. 永久失败

永久失败至少覆盖：

- 卡号无效、余额不足、卡已过期。
- 风控拒绝、商户配置错误、金额或币种非法。
- 网关返回明确的不可重试业务错误码。
- 本地参数校验失败。

预期行为：

- 不创建重试任务，或取消已有未执行任务。
- 支付进入 `FAILED_PERMANENTLY`。
- 原因码被持久化，并可供上层展示或人工处理。
- 不重复调用支付网关。
- 重复提交返回同一个失败结果，而不是生成新支付意图。

还需覆盖错误分类配置变更：分类由配置驱动时，配置加载失败必须采取明确的默认策略，不能把永久失败无限重试。

### 4. 退避策略

假设策略为指数退避：

`delay(n) = min(base_delay * 2^(n-1), max_delay)`

实际延迟为：

`delay_with_jitter = delay(n) * (1 + random_factor)`

测试重点：

- 第 1、2、3 次重试分别符合预期基准值。
- 达到 `max_delay` 后不再增长。
- 抖动结果始终位于配置边界内。
- 重启服务不会重置已执行次数或重新计算为第一次重试。
- 调度器提前触发时不执行任务，必须等到 `next_attempt_at <= now`。
- 同一任务重复投递时只有一个消费者成功领取任务。
- `Retry-After` 存在时，下一次执行时间不早于服务端要求。
- 达到最大次数后不再创建新的重试任务。
- 时钟跨越、夏令时和时区变化不影响延迟计算；内部统一使用 UTC 时间戳。

为避免测试依赖随机数，应注入确定性的随机源或测试随机序列，并验证生产实现仍使用真实随机源。该随机源是测试基础设施，不是业务 mock。

**五、幂等性与并发测试**

### 请求幂等

- 两个并发请求使用相同 `idempotency_key`。
- 一个请求在数据库提交前被中断，随后重复提交。
- 同一幂等键携带不同金额、币种或订单号。
- 服务处理成功后客户端重试请求。

预期：

- 相同参数返回同一支付结果。
- 参数不一致时返回幂等键冲突，不执行网关调用。
- 数据库唯一约束最终保证只有一个支付意图和一个有效网关请求。

### 重试幂等

- 同一个重试任务被两个消费者同时领取。
- 任务执行过程中消费者进程退出，消息重新投递。
- 第一次网关请求已成功，但服务在落库前退出。
- 重试任务与成功回调并发到达。
- 旧版本任务在支付已完成后到达。

预期：

- 网关调用始终使用同一个幂等键。
- 测试网关最终只产生一次扣款。
- 支付状态不会从 `SUCCEEDED` 回退到失败或等待。
- 成功事件使用唯一事件键，重复发布或重复消费不会重复完成订单。

并发测试应实际启动多个服务实例或多个消费者线程，使用真实数据库约束和事务，不通过 mock 验证调用次数。

**六、属性与不变量测试**

对不同错误序列进行参数化测试，例如：

- `[503, 503, success]`
- `[timeout, query-success]`
- `[timeout, query-not-found, success]`
- `[429, 500, permanent-error]`
- `[permanent-error, success]`

必须始终满足：

- 永久失败后不会继续支付重试。
- 成功状态是终态，不会被后续旧消息覆盖。
- 所有重试请求复用原幂等键。
- 实际尝试次数不超过配置上限。
- 每个重试任务的执行时间单调递增。
- 同一支付意图最多产生一个成功扣款结果。
- 金额、币种和订单号在整个重试生命周期内不可变。

**七、故障恢复测试**

在以下阶段主动终止服务并重新启动：

- 创建支付意图后、发送消息前。
- 领取重试任务后、调用网关前。
- 网关响应成功后、数据库提交前。
- 数据库提交后、确认消息前。
- 发布成功事件后、记录事件状态前。

重启后验证任务可恢复、不会丢失，也不会重复扣款。对“网关已受理但本地未知”的阶段，必须验证恢复流程优先查询网关状态。

**八、验证层次**

1. **组件测试**：验证错误分类、退避计算、状态迁移、幂等键校验和最大次数。使用内存中的可控时钟及测试随机源，不替换业务依赖的 mock。
2. **集成测试**：真实数据库、消息队列和测试网关，验证事务、唯一约束、锁、重复投递和重启恢复。
3. **端到端测试**：从支付请求开始，经过队列、重试调度、网关测试端点、订单更新和事件消费，验证最终业务结果。
4. **并发测试**：多个实例同时处理同一请求、同一任务和同一回调，检查真实资源上的竞态。

**九、完成标准**

- 所有核心场景通过，尤其是超时后的未知结果处理。
- 成功、永久失败、最大重试次数和幂等性均有自动化断言。
- 测试网关日志、数据库网关请求记录和订单流水三者一致。
- 任意测试失败时可以定位到支付状态、任务状态和具体尝试序号。
- 集成测试连续运行多次结果稳定，无依赖执行顺序或真实等待时间。
- 监控验证包括：重试次数、按错误码分类的失败数、未知状态数、幂等冲突数、最终成功率和耗尽任务数。
