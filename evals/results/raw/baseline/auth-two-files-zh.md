**目标行为**

访问令牌失效时，认证层应自动完成一次刷新并重放原请求：

1. 首次请求返回 `401`，判定访问令牌可能过期。
2. 认证层启动刷新流程。
3. 刷新成功后更新访问令牌，并使用新令牌重试原请求一次。
4. 重试仍返回 `401` 时立即返回该响应，不再刷新。
5. 刷新失败时向所有等待中的请求返回同一个认证错误，并清理失效凭据。

不应因为一次失效触发多个并发刷新请求，也不应无限重试。

**刷新并发控制**

在认证状态中维护一个共享的刷新 Promise：

```ts
let refreshPromise: Promise<TokenSet> | null = null;
```

刷新入口统一通过 `refreshAccessToken()` 调用：

```ts
function refreshAccessToken(): Promise<TokenSet> {
  if (refreshPromise) {
    return refreshPromise;
  }

  refreshPromise = performRefresh()
    .finally(() => {
      refreshPromise = null;
    });

  return refreshPromise;
}
```

关键规则：

- 第一个检测到过期的请求负责发起刷新。
- 后续并发请求直接复用同一个 Promise。
- 刷新成功后，所有等待请求读取同一组新令牌。
- 刷新成功或失败后都必须清空共享 Promise，避免后续请求永久复用已结束的 Promise。
- 刷新失败时，所有等待者收到同一个错误对象或等价错误信息。
- 刷新接口本身不得经过访问令牌失效重试逻辑，避免递归刷新。
- 如果刷新响应返回新的 refresh token，必须整体替换令牌状态；如果响应未返回新的 refresh token，则保留旧值。

为避免竞态，重放请求前应重新读取当前令牌，而不是使用请求开始时捕获的旧令牌。这样即使某个请求在等待期间没有主动参与刷新，也会使用最新令牌。

**请求重试逻辑**

请求封装层应保留“是否已经因认证失败重试”的标记：

```ts
async function request(input, init, retried = false): Promise<Response> {
  const response = await sendWithCurrentAccessToken(input, init);

  if (response.status !== 401 || retried) {
    return response;
  }

  await refreshAccessToken();

  return request(input, init, true);
}
```

实现时需要注意：

- 只对 `401` 触发刷新；`403` 默认表示权限不足，不应自动刷新。
- 只允许一次刷新和一次重试。
- 原请求的 HTTP 方法、URL、headers、body、credentials、signal 等配置必须保持不变。
- 如果请求 body 是不可重复读取的流，应在首次发送前缓存或拒绝自动重试；不能在重试时发送已消费的 body。
- 重试时只替换认证相关 header，不能覆盖调用方显式设置的其他 header。
- 若调用方取消请求，应尽快结束等待；刷新流程是否可被单个请求取消需要明确区分，不能让一个请求的取消取消掉其他等待者共享的刷新流程。

**令牌状态处理**

成功响应至少应验证：

- 存在非空的 access token。
- `expires_in` 若存在，必须转换为有效的过期时间。
- refresh token 按轮换规则替换或保留。
- 令牌状态更新应一次性完成，避免读取到半更新状态。

建议同时维护绝对过期时间，并在主动请求前预留少量安全窗口，例如提前几十秒视为过期。安全窗口只用于主动刷新，不改变“收到 `401` 后最多重试一次”的规则。

如果访问令牌已过期但 refresh token 不存在，应直接返回未认证错误，不调用刷新接口。

**刷新错误响应**

刷新接口的处理必须覆盖所有非成功响应：

- `2xx`：解析并校验令牌响应。
- `400`：通常表示 refresh token 无效、已撤销或请求参数错误；清理认证状态并返回不可恢复的认证错误。
- `401` 或 `403`：视为 refresh token 已失效；清理认证状态并返回不可恢复的认证错误。
- `429`、`5xx`：视为暂时性刷新失败。默认不自动重试刷新，避免请求风暴；是否保留本地令牌应由现有认证策略决定，但不能把旧 access token 当作刷新成功后的令牌继续重放。
- 其他非 `2xx`：返回包含 HTTP 状态码的认证错误。

错误解析应安全处理：

1. 优先尝试解析 JSON。
2. 从 `error`、`error_description`、`message` 等字段提取稳定信息。
3. JSON 解析失败时读取文本作为有限长度的错误详情。
4. 空响应或非文本响应使用通用错误信息。
5. 错误对象中不得包含 access token、refresh token 或完整请求头。
6. 保留 HTTP 状态码和服务端错误码，方便调用方区分“需要重新登录”和“临时失败”。

建议定义稳定的错误分类：

```ts
type AuthErrorKind =
  | "missing_refresh_token"
  | "invalid_refresh_token"
  | "refresh_failed"
  | "invalid_token_response";
```

不可恢复错误应清理 access token 和 refresh token。暂时性网络错误或服务端 `5xx` 是否清理令牌应保持与现有登录状态约定一致，但不能误判为成功，也不能进入无限重试。

**并发竞态**

需要处理以下场景：

- 两个请求同时收到 `401`：只产生一个刷新请求，两个请求都使用新 token 重试。
- 一个请求已完成刷新，另一个请求随后收到旧 token 导致的 `401`：后者应发现当前令牌版本已变化，优先复用已完成的更新结果或再次进入统一刷新流程，不能覆盖新令牌。
- 刷新响应轮换 refresh token：所有请求必须看到同一组新令牌。
- 刷新失败后立即出现新请求：共享 Promise 已清除，新请求可以重新尝试，但不可复用旧失败结果。
- 刷新接口返回格式错误：视为刷新失败，不更新任何令牌状态。
- 重试请求再次返回 `401`：原样返回响应，不能再次刷新。
- 多个等待者中一个调用方取消：不能影响其他等待者。

如现有实现支持令牌版本号，可在请求发送时记录版本；刷新完成后如果版本已经变化，则直接使用当前状态重试，避免重复刷新和旧响应覆盖新状态。

**回归测试设计**

测试应使用可控的请求 mock，并验证调用次数、请求头、返回值和令牌状态。

核心测试：

1. **单次过期刷新**
   - 首次请求返回 `401`。
   - 刷新返回新 access token。
   - 重试返回成功。
   - 断言原请求发送两次，刷新请求发送一次，第二次请求使用新 token。

2. **并发请求只刷新一次**
   - 同时发起多个请求。
   - 让它们都首次返回 `401`。
   - 刷新接口延迟完成。
   - 断言刷新接口只调用一次。
   - 断言所有请求最终成功且使用同一个新 token。

3. **并发刷新失败**
   - 多个请求同时等待刷新。
   - 刷新返回 `400` 或 `401`。
   - 断言所有请求都失败。
   - 断言只产生一次刷新请求。
   - 断言认证状态已清理。
   - 再发起新请求时不会复用已经 rejected 的 Promise。

4. **刷新后重试仍为 `401`**
   - 首次请求和重试请求都返回 `401`。
   - 断言刷新只调用一次、请求最多发送两次，最终响应仍为 `401`。

5. **`403` 不触发刷新**
   - 请求返回 `403`。
   - 断言刷新接口未调用，响应原样返回。

6. **缺少 refresh token**
   - 访问令牌失效但没有 refresh token。
   - 断言不会调用刷新接口，并返回稳定的未认证错误。

7. **刷新接口错误响应**
   - 分别覆盖 JSON 错误、纯文本错误、空响应、非 JSON 响应。
   - 断言错误包含状态码和可用错误信息。
   - 断言错误中不出现任何令牌值。

8. **服务端临时失败**
   - 刷新返回 `500` 或网络异常。
   - 断言不会将旧 token 当作新 token 使用，也不会无限重试。

9. **refresh token 轮换**
   - 刷新响应同时返回新的 access token 和 refresh token。
   - 断言后续刷新使用新的 refresh token。

10. **刷新响应格式非法**
    - 返回 `2xx` 但缺少 access token。
    - 断言令牌状态不被部分更新，并返回 `invalid_token_response`。

11. **原请求配置保留**
    - 使用 `POST`、自定义 headers 和可复用 body。
    - 断言重试请求完整保留原配置，仅更新认证 header。

12. **主动过期判断**
    - 覆盖未过期、已过期、临近过期和无效 `expires_in`。
    - 断言主动刷新判断符合安全窗口规则。

测试中的刷新延迟应通过手动控制 Promise 完成，避免依赖真实定时器。每个测试都应重置令牌状态、mock 调用记录和共享刷新状态，防止测试之间残留并发 Promise。
