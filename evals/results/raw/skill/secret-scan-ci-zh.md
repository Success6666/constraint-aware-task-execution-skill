下面是一套可落地的代码仓库密钥检测与例外审批流程。

**一、密钥分类与策略**

将扫描结果分为三类：

- **真实凭据**：云厂商 Access Key、数据库密码、私钥、OAuth Token、Webhook Secret 等。
- **疑似凭据**：符合高熵、特定前缀或疑似密钥格式，但无法确认有效性。
- **允许内容**：测试夹具、文档示例、已失效凭据，以及经过审批的例外。

默认策略：

- 未经批准的真实凭据：**阻断提交和 CI**。
- 疑似凭据：阻断合并，除非安全负责人确认误报。
- 允许内容：必须通过精确、可审计的例外规则放行。
- 禁止使用整文件、整目录或宽泛正则进行永久忽略。

**二、本地检查**

在开发者本地提供统一命令，例如：

```bash
make secret-scan
```

检查范围：

1. 工作区未提交文件；
2. 暂存区；
3. 当前分支相对目标分支的 diff；
4. 可选的完整 Git 历史扫描。

建议组合：

- `gitleaks` 或同类规则引擎：检测已知密钥格式；
- 高熵字符串和私钥头检测；
- `.env`、配置文件、Terraform、Kubernetes YAML 等重点路径扫描；
- 对云厂商密钥执行轻量在线有效性验证（仅在安全网络和受控凭据下启用）。

提交钩子：

```bash
pre-commit:
  - secret-scan --staged
```

本地命令输出应包含：

- 文件和行号；
- 规则 ID；
- 匹配类型；
- 修复建议；
- 例外申请链接。

本地扫描失败不能被“跳过提交”视为批准；`SKIP=secret-scan` 只允许在紧急调试时使用，并在 CI 中重新强制检查。

**三、CI 强制门禁**

在以下流水线阶段执行：

1. Pull Request：扫描变更 diff；
2. 主分支合并前：扫描完整仓库；
3. 定期任务（例如每日）：扫描完整 Git 历史和制品；
4. 发布流水线：扫描构建产物、镜像层和生成配置。

示例：

```yaml
secret_scan:
  stage: security
  image: zricethezav/gitleaks:latest
  script:
    - gitleaks detect --source . --redact --report-format sarif --report-path gitleaks.sarif
  artifacts:
    reports:
      sast: gitleaks.sarif
  allow_failure: false
```

门禁规则：

- 检测到**未经批准的真实凭据**时，作业必须返回非零状态，CI 失败，禁止合并和发布。
- 任何“已验证有效”的凭据都必须自动升级为最高优先级事件。
- CI 不接受开发者在代码中的 `nosec`、`ignore` 或类似注释作为放行依据。
- 例外清单必须由受保护分支维护，并由 CODEOWNERS 指定安全团队审批。

建议设置超时和重试，避免在线验证服务故障导致误判；但扫描器本身不可用时应按“失败关闭”处理，除非安全负责人临时批准并记录事件编号。

**四、误报处理与例外审批**

例外记录应集中在版本控制中的机器可读文件，例如：

```yaml
exceptions:
  - id: EX-2026-001
    rule: generic-high-entropy
    path: tests/fixtures/sample-token.txt
    fingerprint: "sha256:..."
    reason: "固定测试数据，不具备认证能力"
    owner: team-payments
    approver: security@example.com
    expires: 2026-12-31
    compensating_control: "仅测试环境使用"
```

审批要求：

- 申请人不能审批自己的例外；
- 至少一名代码所有者和一名安全负责人审批；
- 必须填写路径、规则 ID、指纹、理由、风险、补偿控制和到期日；
- 例外默认最多 90 天，到期自动失效；
- 修改例外文件也触发安全团队审查；
- 例外必须绑定内容指纹，文件内容变化后自动重新告警；
- 禁止使用 `*`、整个目录或无期限例外。

误报处理流程：

1. CI 创建安全工单并标记提交；
2. 开发者提交例外申请或移除敏感内容；
3. 安全人员确认是否为真实凭据；
4. 若为误报，加入最小范围例外并设置到期日；
5. 若无法确认，按真实凭据处理，不允许直接放行。

**五、发现真实凭据后的响应与轮换**

一旦确认真实凭据：

1. 立即阻断 CI、合并和发布；
2. 在密钥提供方撤销或禁用凭据；
3. 创建替换凭据，并通过 CI/CD Secret Manager 注入；
4. 检查访问日志、使用范围和潜在数据暴露；
5. 从当前分支和 Git 历史中移除明文；
6. 必要时清理镜像、缓存、构建产物和制品仓库；
7. 记录事件、时间线、影响范围和责任人；
8. 完成复盘并更新检测规则或测试。

重要原则：**从 Git 删除字符串不等于凭据失效**，轮换和撤销必须先于历史清理。

凭据生命周期应包含：

- 创建：仅由密钥管理系统生成；
- 使用：短期、最小权限、按环境隔离；
- 轮换：定期自动轮换，或事件触发立即轮换；
- 失效：离职、项目结束、权限变更时撤销；
- 审计：记录读取、使用、轮换和撤销日志。

**六、测试方案**

将密钥检测作为安全测试的一部分：

- 单元测试：每条自定义规则至少包含正例、负例和边界样例；
- 回归测试：保存历史误报样本，确保规则调整不会重复触发；
- CI 集成测试：向临时分支注入假密钥，确认作业失败；
- 例外测试：验证有效例外可放行，过期、指纹变化、未审批例外必须失败；
- 历史扫描测试：验证已提交到旧 commit 的凭据仍能被发现；
- 制品测试：扫描 Docker 镜像、压缩包和生成配置；
- 轮换演练：定期验证撤销、替换、服务恢复和审计告警；
- 旁路测试：验证 `SKIP`、忽略注释和本地禁用钩子不会绕过 CI 门禁。

发布前应至少验证以下断言：

```text
未经批准的真实凭据 -> secret-scan 非零退出 -> CI 失败 -> 禁止合并
已批准且未过期的精确例外 -> 可放行
过期或内容变化的例外 -> CI 失败
扫描器不可用 -> CI 失败关闭
```

**七、职责与审计**

- 开发团队：修复泄露、提交例外申请、维护测试数据；
- 代码所有者：确认业务上下文和最小范围；
- 安全团队：判断真实性、审批例外、处置事件；
- 平台团队：维护扫描器、CI 门禁和密钥管理集成。

所有扫描结果、审批、例外变更、轮换和处置记录保留审计日志，至少覆盖凭据生命周期和例外有效期。
