## 修复方案

### 1. 统一过期判断与错误模型

- 将 `401` 作为访问令牌失效的主要信号；同时兼容响应体中明确表示 token expired/invalid 的业务错误码。
- 仅在“令牌过期或无效”时触发刷新；权限不足、参数错误、服务端错误等响应直接返回，不得误刷新。
- 定义统一的认证错误结果，至少包含：HTTP 状态码、业务错误码、用户可识别的 message，以及原始响应信息，避免调用方收到不一致的异常类型。

### 2. 刷新并发控制

- 使用模块级 `refreshPromise` 作为 single-flight 锁：
  - 没有刷新任务时创建刷新请求并保存 Promise。
  - 后续并发请求发现已有 Promise 时直接复用，不再发起新的刷新请求。
  - 刷新 Promise 无论成功或失败，都必须在 `finally` 中清空，防止后续请求永久复用已结束的 Promise。
- 刷新成功后，以服务端返回的新 access token 同时更新内存状态和持久化状态；如有 refresh token 轮换，也必须同步保存新的 refresh token。
- 刷新请求本身不得再次进入自动刷新流程，否则会形成递归或死循环。

### 3. 请求重试策略

- 原请求携带旧 token 返回过期错误后：
  1. 等待共享的刷新 Promise。
  2. 使用最新 token 重建认证头。
  3. 原请求仅重试一次。
- 用请求级标记（例如 `retried`）限制重试次数，而不是依赖全局状态。
- 重试时重新生成请求头，不能继续使用已被修改或缓存的旧 Authorization 值。
- 并发请求在刷新完成后都使用同一个新 token；刷新期间新发起且需要认证的请求也应等待该刷新任务，避免继续使用已知失效 token。

### 4. 刷新失败与错误响应

- 刷新接口返回 `401/403`、refresh token 失效或明确认证失败时：
  - 清除 access token、refresh token 及相关认证状态。
  - 返回统一的“需要重新登录”错误。
  - 所有等待同一刷新 Promise 的请求收到同一个认证失败结果。
- 刷新接口返回网络错误、超时或 `5xx` 时：
  - 不伪造成功响应，也不无限重试。
  - 保留原始错误上下文，包装成可识别的刷新失败错误后向调用方抛出。
  - 是否清除本地 token 应按现有认证策略处理；至少不能把失败刷新结果写入 token 存储。
- 重试后的请求再次返回认证失败时，直接返回统一错误，不再触发第二次刷新。
- 非认证类错误保持原有状态码、业务错误码和响应体，避免改变既有调用方行为。

### 5. 状态一致性与边界处理

- token 更新必须是原子的：先确认刷新响应包含有效 access token，再更新认证状态。
- 刷新成功后清除旧 token，避免后续请求意外读取旧值。
- 刷新响应缺少 token、格式非法或无法解析时，按刷新失败处理，不更新任何认证状态。
- 清除认证状态和刷新 Promise 的生命周期相互独立，确保失败后下一次请求仍可重新建立刷新流程。

## 回归测试设计

使用可控的请求 mock、刷新接口 mock 和 token 存储 mock，至少覆盖以下场景：

1. **正常请求**：有效 token 请求成功，刷新接口未被调用。
2. **单次过期重试**：原请求第一次返回认证过期，刷新成功，随后使用新 token 重试并返回原业务结果。
3. **并发刷新合并**：同时发起多个过期请求，断言刷新接口只调用一次，所有请求最终使用同一新 token 成功。
4. **刷新期间新请求**：刷新尚未完成时发起另一认证请求，断言该请求等待同一刷新任务，而不是使用旧 token 或再次刷新。
5. **刷新认证失败**：刷新返回 `401/403`，断言所有等待请求收到统一登录失效错误，token 被清除，刷新 Promise 已释放。
6. **刷新网络失败或 `5xx`**：断言错误被正确传递、不发生无限重试，后续请求仍能重新尝试刷新。
7. **重试再次过期**：刷新成功但重试仍返回 `401`，断言最多只请求两次且不会循环刷新。
8. **非认证错误**：原请求返回 `400/403（权限不足）/404/500` 等非过期错误，断言不调用刷新且保留原错误信息。
9. **刷新响应非法**：刷新返回缺少 token 或无效格式，断言不覆盖旧状态，并返回刷新失败错误。
10. **token 持久化**：刷新成功后断言内存和持久化存储均为新 token；失败后断言不会写入无效 token。
11. **刷新锁释放**：一次刷新失败后，再次触发过期请求能够创建新的刷新任务，证明不会卡在已拒绝的 Promise 上。
12. **请求头更新**：断言重试请求使用新 Authorization 值，且不会复用旧请求头对象。

测试还应验证 Promise 拒绝路径和请求 mock 的调用顺序，确保并发场景不是仅通过最终返回值“碰巧”通过。
