## 支付重试服务测试方案

### 1. 测试目标

验证支付重试服务能够：

- 首次支付成功时立即完成，不产生多余重试。
- 正确识别网络超时、连接中断、限流和服务端错误等瞬时失败。
- 正确识别拒付、参数错误、鉴权失败等永久失败。
- 按配置执行指数退避、最大间隔和最大重试次数。
- 在重复请求、并发请求、响应丢失和服务重启场景下保持幂等。

### 2. 测试环境

采用与生产链路一致的真实组件：

- 独立启动支付重试服务进程。
- 使用容器化 PostgreSQL、Redis、消息队列等实际依赖。
- 接入支付渠道官方 Sandbox。
- 使用 Toxiproxy 在服务与支付 Sandbox 之间注入超时、断连、延迟等网络故障。
- 使用真实调度器和系统时钟。
- 开启结构化日志、支付尝试记录和指标采集。

建议测试配置：

```yaml
retry:
  max-attempts: 4
  initial-delay: 200ms
  multiplier: 2
  max-delay: 1s
  jitter: 0
```

短间隔仅用于缩短测试时间，算法和生产配置保持一致。抖动单独测试。

### 3. 核心测试矩阵

| 编号 | 场景 | 故障注入/输入 | 预期结果 |
|---|---|---|---|
| PAY-01 | 首次成功 | Sandbox 成功支付方式 | 只调用渠道一次，订单和支付记录均成功 |
| PAY-02 | 超时后成功 | 首次阻断响应，随后恢复网络 | 自动重试并成功，业务只入账一次 |
| PAY-03 | 连接中断后成功 | 前两次断开连接，第三次恢复 | 共执行三次尝试，最终成功 |
| PAY-04 | 渠道 5xx 后成功 | Sandbox 可用时结合故障代理制造服务不可达 | 状态保持可重试，恢复后成功 |
| PAY-05 | 渠道限流 | 使用 Sandbox 限流能力或真实测试限额 | 遵循 `Retry-After` 或内部退避策略 |
| PAY-06 | 永久拒付 | Sandbox 拒付测试卡 | 立即失败，不进入重试队列 |
| PAY-07 | 参数错误 | 提交渠道明确拒绝的参数 | 记录永久失败，不重试 |
| PAY-08 | 鉴权失败 | 使用无效 Sandbox 凭据 | 立即终止，产生告警，不重复请求 |
| PAY-09 | 达到重试上限 | 持续阻断渠道连接 | 尝试次数达到上限后进入最终失败状态 |
| PAY-10 | 指数退避 | 连续制造可重试失败 | 各次尝试间隔符合配置 |
| PAY-11 | 最大退避上限 | 增加重试次数 | 间隔增长到上限后不再增加 |
| PAY-12 | 幂等重复提交 | 相同幂等键连续提交多次 | 返回同一支付结果，只产生一笔业务支付 |
| PAY-13 | 幂等并发提交 | 20 个并发请求使用相同幂等键 | 仅一个请求执行支付，其余复用结果或等待 |
| PAY-14 | 渠道成功但响应丢失 | 请求到达 Sandbox 后阻断响应 | 重试使用同一幂等键，渠道只产生一笔支付 |
| PAY-15 | 重试期间服务重启 | 首次失败后停止并重启服务 | 重试任务不丢失，恢复后继续执行 |
| PAY-16 | 已成功任务重复投递 | 重复投递同一支付消息 | 不再次扣款，消费者正常确认消息 |

### 4. 关键用例步骤

#### PAY-02：瞬时失败后成功

1. 创建唯一订单和幂等键。
2. 通过 Toxiproxy 阻断支付响应。
3. 发起支付，确认第一次尝试记录为可重试失败。
4. 恢复网络连接。
5. 等待调度器执行下一次尝试。
6. 查询 Sandbox、订单表、支付表和账务表。

验收标准：

- 最终支付状态为成功。
- 尝试次数符合预期。
- 每次尝试使用相同幂等键。
- Sandbox 中只有一个支付对象和一次资金结果。
- 本地只存在一条有效账务记录。

#### PAY-06：永久失败

1. 使用 Sandbox 提供的拒付测试支付方式。
2. 发起支付。
3. 等待超过首个重试间隔。
4. 查询重试任务和支付尝试记录。

验收标准：

- 支付状态为最终失败。
- 失败原因和渠道错误码被保存。
- 尝试次数为一次。
- 不存在待执行的重试任务。
- 不生成成功账务记录。

#### PAY-10：指数退避

从持久化尝试记录中读取每次实际开始时间：

```text
d1 = attempt2.started_at - attempt1.finished_at
d2 = attempt3.started_at - attempt2.finished_at
d3 = attempt4.started_at - attempt3.finished_at
```

配置为 `200ms、400ms、800ms` 时，考虑调度和系统负载，允许例如 `±100ms` 的执行误差。断言应覆盖：

- 延迟按倍率增长。
- 延迟不超过最大值。
- 等待期间没有提前执行。
- 达到最大次数后不再生成新任务。

启用抖动时，不断言精确时间，而是断言每次延迟位于策略规定区间内。

#### PAY-14：未知支付结果下的幂等性

1. 使用唯一订单号和渠道幂等键发起支付。
2. 让请求到达 Sandbox，但通过故障代理阻断返回数据。
3. 服务将本次尝试记录为结果未知。
4. 恢复连接，触发重试。
5. 查询渠道最终交易及本地账务。

验收标准：

- 所有尝试使用相同渠道幂等键。
- 渠道返回同一支付对象或交易编号。
- 用户只被扣款一次。
- 本地只入账一次。
- 最终状态能够从“结果未知”收敛为成功。

### 5. 数据与并发校验

数据库至少检查以下约束：

- `idempotency_key` 或业务支付号具有唯一约束。
- 同一订单最多存在一条有效成功支付。
- 重试次数递增操作具备事务一致性。
- 支付状态只能按合法状态机迁移。
- 消息重复消费不会重复写入账务流水。
- 多实例竞争任务时，仅一个实例获得执行权。

并发用例应通过线程池或多进程同时发送真实 HTTP 请求，并使用屏障统一释放请求，避免普通循环无法形成有效竞争。

### 6. 可观测性断言

每次尝试应能关联以下字段：

```text
order_id
payment_id
idempotency_key
attempt_number
provider_request_id
provider_payment_id
failure_category
next_retry_at
final_status
```

同时验证指标：

- 支付尝试总数。
- 重试成功数。
- 永久失败数。
- 重试耗尽数。
- 重试延迟分布。
- 幂等冲突或重复请求数。

日志和指标不得包含银行卡号、验证码、完整凭据等敏感信息。

### 7. 通过标准

- 所有核心用例稳定连续通过至少 3 次。
- 每种失败都被归类为“可重试”或“永久失败”，不存在无限重试。
- 退避间隔、最大次数和最大间隔符合配置。
- 并发重复请求、消息重复投递及响应丢失均不会造成重复扣款或重复入账。
- 服务重启后重试任务不丢失、不提前执行。
- 测试结束后可通过订单号和渠道交易号完整追溯支付过程。
