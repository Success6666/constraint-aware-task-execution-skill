以下方案以“真实 HTTP 交互”为边界：支付服务连接支付沙箱；对沙箱前的故障注入层使用独立进程，可返回指定状态、延迟响应或断开连接，不使用进程内替身或 mock 框架。最终是否扣款以支付网关账本和订单数据库为准。

## 1. 测试配置

测试环境建议提供可配置参数：

- 初始退避：`100 ms`
- 退避倍数：`2`
- 最大退避：`2 s`
- 最大尝试次数：`4`
- 抖动：`full jitter`，即每次等待时间在 `0..计算值` 内随机
- 幂等键：由业务请求传入，并在所有重试请求中保持不变
- 每次尝试记录：请求 ID、幂等键、尝试序号、开始时间、结束时间、响应类型

测试数据：

- 一笔金额固定、可在沙箱中支付的订单
- 一个唯一幂等键，例如 `order-1001-payment`
- 一个可查询交易状态的沙箱账户
- 一个可清空、可查询的支付网关交易账本

## 2. 核心测试矩阵

| 场景 | 网关行为 | 预期结果 |
|---|---|---|
| 首次成功 | 第 1 次返回成功 | 订单标记为已支付；只产生 1 笔扣款；不再重试 |
| 瞬时失败后成功 | 前 2 次返回 `500`，第 3 次成功 | 共 3 次尝试；订单最终成功；只产生 1 笔扣款 |
| 429 限流后成功 | 第 1 次返回 `429`，带 `Retry-After`，随后成功 | 优先遵循 `Retry-After`；成功后停止 |
| 连接超时后成功 | 第 1 次请求延迟超过客户端超时，第 2 次成功 | 进入重试；确认不会因超时造成重复扣款 |
| 瞬时失败耗尽 | 每次返回 `502` 或超时，达到最大次数 | 订单进入可重试失败/人工处理状态；不再继续请求；无成功支付标记 |
| 永久失败 | 返回 `400`、`401`、`403`、参数校验错误 | 只请求 1 次；立即失败；不触发重试 |
| 业务拒付 | 返回支付网关定义的永久拒付码 | 不重试；订单标记为支付失败，并保留明确失败原因 |
| 混合失败 | 第 1 次 `500`，第 2 次 `400` | 第 2 次后立即停止，不再执行后续重试 |
| 网关已扣款但响应丢失 | 网关记账成功，客户端收到连接断开 | 重试必须复用同一幂等键；最终只能有 1 笔扣款，并通过查询或幂等响应恢复状态 |

每个场景都应检查：

1. 最终订单状态。
2. 支付网关账本中的交易数量和金额。
3. 实际 HTTP 请求次数及顺序。
4. 重试任务是否被正确清理或安排。
5. 日志、指标和错误原因是否准确。

## 3. 退避测试

### 3.1 计算正确性

将基础参数设为较小值以缩短测试时间，例如：

- `base = 100 ms`
- `multiplier = 2`
- `maxDelay = 1 s`
- 最大尝试次数 `4`

在连续瞬时失败后，记录每次请求的时间戳，验证：

- 第一次失败后等待时间处于 `0..100 ms`。
- 第二次失败后等待时间处于 `0..200 ms`。
- 第三次失败后等待时间处于 `0..400 ms`。
- 后续等待时间不超过 `1 s`。
- 不允许出现紧接着的忙循环请求。
- 达到最大尝试次数后不再创建新的重试任务。

由于存在抖动，不应断言精确毫秒值，而应断言时间区间和上限。

### 3.2 `Retry-After` 优先级

配置网关返回：

- `429` + `Retry-After: 2`
- `503` + `Retry-After: 1`

验证实际下一次请求不会早于指定时间；同时验证服务仍受全局最大退避限制约束，避免网关返回异常大值导致任务永久挂起。

### 3.3 重启和持久化

在等待退避期间停止并重新启动支付服务，验证：

- 已安排的重试不会丢失。
- 不会重置为第 1 次尝试。
- 不会因为重启立即重复发送请求。
- 任务恢复后仍使用原始幂等键和原始订单号。

## 4. 幂等性测试

### 4.1 相同请求重复提交

对同一订单、相同金额、相同幂等键连续提交两次：

- API 可以返回相同的成功结果，或第二次返回“已处理”。
- 网关账本只能有 1 笔扣款。
- 订单只能产生一个支付成功事件。

### 4.2 并发提交

并发发送 10 个完全相同的支付请求，验证：

- 最终只有 1 笔扣款。
- 只有 1 个请求真正完成扣款，其余请求读取同一结果或进入处理中状态。
- 数据库不会产生重复支付记录。
- 不会发送多个不同的幂等键给网关。

### 4.3 相同幂等键、不同参数

先以金额 `100` 提交幂等键 `K1`，再以金额 `200` 使用同一 `K1` 提交：

- 请求必须被拒绝，返回幂等键冲突。
- 不得修改原交易金额。
- 不得产生第二笔扣款。

### 4.4 重试链路中的幂等键

让第一次请求在网关侧成功、客户端侧超时，随后触发重试，验证所有尝试的：

- 幂等键相同。
- 订单号相同。
- 业务金额相同。
- 网关最终仍只有一笔交易。

## 5. 非功能与边界检查

- 重试任务具有唯一任务标识，避免同一订单同时存在多个活动重试任务。
- 永久失败不会进入重试队列。
- 瞬时失败耗尽后必须有明确的终态和人工补偿路径。
- 指标至少包含：首次成功率、重试成功率、最终失败率、按原因分类的尝试次数、重复幂等命中次数。
- 日志中不得记录完整卡号、CVV 等敏感数据。
- 验证金额使用整数最小货币单位，重试不会发生金额变化或重复累加。

## 6. 自动化分层

1. **支付服务到故障注入层的集成测试**：验证 HTTP 状态、超时、断连、退避和重试次数。
2. **支付服务到沙箱的端到端测试**：验证真实授权、扣款、查询和网关账本。
3. **数据库与任务恢复测试**：验证重启、并发唯一约束和重试任务持久化。
4. **定时稳定性测试**：连续运行多轮瞬时失败、超时和重复提交，观察是否出现重复扣款或任务泄漏。

## 7. 通过标准

- 所有成功场景最终只有一笔有效扣款。
- 永久失败零重试。
- 瞬时失败严格遵循最大尝试次数和退避上限。
- 重启后任务和尝试次数保持一致。
- 相同幂等键的重复及并发请求均不会重复扣款。
- 网关账本、订单状态、请求日志三者能够相互核对。
