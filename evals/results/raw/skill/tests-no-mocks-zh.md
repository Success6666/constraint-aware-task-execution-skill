支付重试服务应以集成测试和端到端测试为主，使用真实数据库、真实消息队列以及支付服务商的 Sandbox 环境。测试替身只用于模拟支付服务商明确提供的错误响应场景，采用可编排的本地 HTTP 测试服务或服务商 Sandbox 测试卡，不使用 Mock 对象。

**一、测试环境**

- 独立测试数据库，验证订单、支付尝试记录和幂等键的真实持久化行为。
- 真实消息队列或任务调度器，验证重试任务是否实际投递、延迟和恢复。
- 支付服务商 Sandbox，优先使用其成功、超时、限流、余额不足、卡失效等测试场景。
- 可控制响应和延迟的 HTTP 测试服务，用于无法由 Sandbox 稳定触发的网络错误、连接中断和 5xx。
- 使用可推进的测试时钟或等待真实调度时间；不要通过替换业务依赖来绕过重试逻辑。

**二、核心场景**

| 场景 | 初始响应 | 预期行为 |
|---|---|---|
| 首次成功 | 2xx，返回交易号 | 状态变为 `succeeded`，不再重试，订单只记账一次 |
| 第二次成功 | 第一次超时或 503，第二次 2xx | 产生两次支付尝试，最终成功，记录失败原因和最终交易号 |
| 连续瞬时失败后成功 | 多次 408/429/502，之后成功 | 按策略重试，达到成功条件后停止 |
| 达到最大次数 | 每次均为 503 或超时 | 状态变为 `retry_exhausted` 或进入人工处理，不再继续投递 |
| 永久失败 | 400、余额不足、卡失效、参数错误 | 立即标记 `permanently_failed`，不进行重试 |
| 服务重启恢复 | 任务执行过程中重启服务 | 未完成任务可恢复，不能丢失或重复创建不可控的支付请求 |
| 响应丢失 | 支付方已扣款，但客户端未收到响应 | 通过查询接口或幂等键确认结果，不能再次扣款 |
| 重复消息 | 同一个重试任务投递两次 | 只有一个有效支付结果，另一条被安全跳过 |
| 并发请求 | 同一订单同时触发多个支付请求 | 只有一个请求进入支付流程，其余返回已有结果或冲突状态 |

**三、退避测试**

假设策略为：

```text
delay(n) = min(baseDelay * 2^(n-1), maxDelay) + jitter
```

验证：

- 第 1、2、3 次重试的延迟符合配置范围。
- 延迟不会小于最小值，也不会超过最大值。
- 达到最大重试次数后不会继续创建任务。
- 429 响应携带 `Retry-After` 时，按协议优先采用服务端建议值。
- 抖动值位于规定范围，避免多个任务同时重试。
- 服务重启后，已持久化的 `next_retry_at` 不会被重置。
- 系统时间变化或重复消费任务时，不会提前执行重试。

测试时记录任务创建时间、计划执行时间和实际执行时间，断言允许一个明确的调度误差范围，而不是断言精确毫秒值。

**四、幂等性测试**

使用同一个业务幂等键，例如 `merchant_id + order_id + payment_attempt_id`：

1. 同一请求提交两次，响应应一致，最多产生一个支付交易。
2. 第一次请求超时后重复提交，支付方最终只能有一个交易。
3. 同一幂等键携带不同金额、币种或订单号，应返回参数冲突，而不是复用旧结果。
4. 请求成功但服务在写库前崩溃，恢复后重试不能造成二次扣款。
5. 请求失败后重试，历史尝试记录完整，幂等键状态可追踪。
6. 并发提交相同幂等键，验证数据库唯一约束或事务锁真正生效。
7. 幂等记录过期后再次使用时，行为符合业务规定，并有明确的保留周期。

重点断言支付服务商侧的真实交易数量，而不只是本地数据库中的调用次数。

**五、数据与状态断言**

每个测试都应检查：

- 支付状态流转是否合法：`pending -> retrying -> succeeded/permanently_failed/retry_exhausted`。
- 每次尝试的序号、请求时间、响应码、错误分类和交易号。
- 重试任务的状态、`next_retry_at`、失败原因和最大次数。
- 订单金额、库存、发票或账务记录不会重复生成。
- 日志和指标包含订单号、幂等键、尝试次数及最终结果，但不泄露完整卡号或敏感数据。

**六、测试组织**

- `payment_retry_success`
- `payment_retry_transient_failure`
- `payment_retry_permanent_failure`
- `payment_retry_backoff`
- `payment_retry_idempotency`
- `payment_retry_recovery`
- `payment_retry_concurrency`

每个测试开始时创建独立订单和幂等键，结束后清理测试数据，并保存支付 Sandbox 的交易记录作为审计依据。CI 中运行稳定、耗时可控的 Sandbox 集成测试；网络抖动、服务重启和长退避场景放入定时端到端测试。
