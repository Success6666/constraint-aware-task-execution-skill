建议采用“本地快速反馈 + CI 强制门禁 + 集中例外台账 + 事件化轮换”的流程。核心原则是：**任何未经批准的真实凭据，一经发现必须阻断 CI；正在使用的真实凭据不得通过例外放行。**

## 1. 检测范围

同时使用两类规则：

- 已知模式：云厂商密钥、GitHub Token、私钥、数据库连接串、JWT、Webhook Secret 等。
- 熵与上下文检测：识别高随机字符串，并结合变量名、文件路径和附近文本降低误报。
- 历史扫描：首次上线或定期扫描完整 Git 历史。
- 增量扫描：本地和 PR CI 只扫描暂存内容或目标分支以来的提交。
- 编码检测：覆盖 Base64、URL 编码和常见字符串拼接。
- 文件类型：源代码、配置、脚本、文档、测试数据、容器文件、IaC 文件均纳入扫描。
- 默认排除依赖目录和构建产物，但排除规则必须集中维护并接受评审。

扫描结果至少包含规则编号、文件、行号、指纹和修复指引；日志中不得输出完整密钥，只显示脱敏片段。

## 2. 本地检查

在 `pre-commit` 中运行增量扫描：

```text
开发者提交
  -> 扫描暂存文件
  -> 无发现：允许提交
  -> 有发现：阻止提交并显示修复或申请例外的方法
```

同时提供显式命令：

```text
secret-scan staged
secret-scan branch origin/main
secret-scan repository-history
```

本地钩子用于快速反馈，但不能作为唯一控制，因为它可以被跳过。仓库应提供统一安装脚本，并在开发环境初始化时自动启用。

## 3. CI 强制门禁

在 PR、合并队列以及受保护分支的直接推送上运行扫描：

1. 扫描 PR 相对于目标分支新增的内容。
2. 校验命中的例外是否存在、有效、未过期且与当前指纹完全匹配。
3. 扫描器故障、配置无法解析或例外校验失败时，采用 fail-closed 策略。
4. 发现未经批准的疑似凭据时阻断 CI。
5. 经过验证属于真实凭据时，无论是否已经从当前提交删除，都必须进入泄露响应流程；在轮换完成前 CI 保持失败。
6. 受保护分支将该检查设置为必需状态检查，任何角色都不能通过普通合并操作绕过。

建议将扫描器和规则版本固定，更新通过依赖升级 PR 完成。CI 输出上传脱敏的 SARIF 或 JSON 报告，并限制报告访问权限。

判定逻辑可以明确为：

```text
扫描器异常                         -> CI 失败
新增命中且没有有效例外             -> CI 失败
命中真实、仍有效或状态未知的凭据   -> CI 失败，并要求轮换
命中已撤销凭据但没有事件记录       -> CI 失败
命中有效的测试夹具例外             -> CI 通过并记录审计信息
例外过期、范围扩大或内容指纹变化   -> CI 失败
```

## 4. 误报与例外审批

例外只允许用于确认无效的测试数据、文档示例、扫描器缺陷等情况，不能用于活跃生产凭据。例外台账应存放在独立的受保护文件中，例如：

```yaml
exceptions:
  - id: SEC-2026-0042
    fingerprint: "sha256:..."
    rule: "generic-high-entropy"
    path: "test/fixtures/oauth_response.json"
    lines: "12-12"
    reason: "供应商公开文档中的不可用示例值"
    classification: "false-positive"
    owner: "payments-team"
    approved_by:
      - "security-reviewer"
      - "repository-owner"
    created_at: "2026-08-16"
    expires_at: "2026-11-16"
```

审批要求：

- 申请人不能审批自己的例外。
- 至少由安全负责人和代码所有者审批。
- 例外绑定规则、路径、行范围和内容指纹，禁止宽泛路径通配。
- 默认有效期不超过 90 天，到期必须重新确认。
- 例外变更由 `CODEOWNERS` 强制安全团队评审。
- CI 不接受提交信息、代码注释或扫描器内联注释中的临时忽略。
- 每次例外使用都写入审计记录，并定期清理未使用或到期例外。

若不能确认是真实凭据还是误报，应按真实泄露处理，而不是先放行。

## 5. 密钥泄露与轮换

发现真实凭据后立即执行：

1. CI 失败，并创建安全事件或工单。
2. 撤销或禁用旧凭据，优先于清理 Git 历史。
3. 检查提供方审计日志，确定使用时间、来源和影响范围。
4. 创建权限最小、有效期更短的新凭据。
5. 将新值写入密钥管理系统，由运行时注入，不提交到仓库。
6. 更新所有使用方并验证服务正常。
7. 再次扫描当前分支和完整历史。
8. 必要时清理 Git 历史，并通知所有克隆仓库重新同步。
9. 记录撤销证据、轮换时间、影响评估和事件负责人。
10. 安全人员确认旧凭据已失效后，才允许 CI 恢复通过。

仅删除文件或重写提交不能证明风险已经解除。密钥一旦进入 Git、CI 日志或构建产物，就应视为已经泄露。

## 6. 测试方案

检测规则测试：

- 每种受支持的凭据类型提供无效的合成样本。
- 验证明文、编码、配置文件、脚本和多行私钥检测。
- 验证普通 UUID、哈希、锁文件等不会产生不可接受的误报。

门禁测试：

- 未批准的合成凭据必须导致 CI 失败。
- 有效且精确匹配的测试例外可以通过。
- 过期、被篡改、扩大路径范围或缺少审批的例外必须失败。
- 扫描器退出异常、配置损坏或报告缺失必须失败。
- 从最新提交删除但仍存在于本次 PR 历史中的凭据必须失败。
- 日志和制品中不得出现完整样本值。

轮换演练：

- 至少每季度执行一次模拟泄露。
- 验证撤销权限、负责人、通知渠道和审计日志可用。
- 记录发现时间、撤销时间和恢复时间，持续缩短响应时长。

## 7. 治理指标

持续跟踪：

- 未批准密钥进入默认分支的数量，目标为零。
- 从发现到撤销的平均时间。
- 误报率和例外数量。
- 过期例外数量。
- 未完成轮换事件数量。
- 扫描覆盖率，包括 PR、默认分支和 Git 历史。

最终责任边界应清晰：开发团队负责移除和修复，安全团队负责例外审批与事件关闭，平台团队负责 CI 门禁不可绕过及扫描器可用性。
