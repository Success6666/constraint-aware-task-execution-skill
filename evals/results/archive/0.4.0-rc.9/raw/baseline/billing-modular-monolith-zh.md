# 模块化单体计费系统设计

采用单一可部署、单一进程或单一运行单元的应用，但在代码、数据访问和事务上严格划分模块边界。模块之间通过应用服务和进程内事件交互，不通过跨模块直接访问数据库表，也不以网络调用模拟微服务。

## 1. 模块划分与边界

### 订阅模块

负责客户与计费方案之间的商业关系。

职责：

- 创建、变更、暂停、恢复、取消订阅
- 管理套餐、价格版本、计费周期
- 处理生效时间、试用期、升级降级和按比例计费策略
- 维护订阅状态历史

核心实体：

- `Customer`
- `Plan`
- `Price`
- `Subscription`
- `SubscriptionItem`
- `SubscriptionChange`

不负责：

- 计算实际用量
- 生成最终账单
- 发起扣款

对外提供：

- 查询当前有效订阅和价格
- 根据时间点解析计费项目
- 发布 `SubscriptionActivated`、`SubscriptionChanged`、`SubscriptionCanceled`

### 计量模块

负责记录和汇总资源使用量。

职责：

- 接收幂等的用量事件
- 校验资源、租户和计量单位
- 保存原始用量记录
- 按订阅、计费周期聚合用量
- 记录修正、冲正和重放信息

核心实体：

- `UsageRecord`
- `UsageAdjustment`
- `UsageAggregate`
- `MeterDefinition`

不负责：

- 决定价格
- 修改订阅状态
- 创建支付订单

关键约束：

- `event_id` 或业务幂等键必须唯一
- 原始记录不可变，修正通过新记录或调整记录完成
- 聚合数据可重建，不能作为唯一事实来源

对外提供：

- 查询某订阅在某周期内的计量结果
- 发布 `UsagePeriodClosed` 或 `UsageAdjusted`

### 账单模块

负责根据订阅和用量形成应收款项。

职责：

- 创建账单周期
- 根据价格、固定费用、阶梯价格和用量计算明细
- 处理折扣、税费、信用额度和舍入
- 生成账单、账单明细和应收款
- 维护账单状态及调整单

核心实体：

- `BillingPeriod`
- `Invoice`
- `InvoiceLine`
- `CreditNote`
- `Receivable`

账单生成时只读取：

- 订阅模块提供的有效订阅快照
- 计量模块提供的周期用量快照

生成后的账单必须保存价格、税率、折扣和计算结果快照，不能依赖后续价格变化重新解释历史账单。

不负责：

- 直接调用支付渠道
- 保存支付渠道返回的交易状态

对外提供：

- 预览账单
- 生成、确认、作废账单
- 查询应收余额
- 发布 `InvoiceIssued`、`InvoiceOverdue`、`InvoiceSettled`

### 支付模块

负责应收款项的收款和退款。

职责：

- 创建支付意图或支付订单
- 管理支付渠道适配器
- 处理支付回调和异步通知
- 记录支付、退款、失败和重试
- 将支付结果关联到账单应收款

核心实体：

- `Payment`
- `PaymentAttempt`
- `Refund`
- `PaymentMethod`
- `WebhookReceipt`

支付状态与账单状态分离：

- 支付：`Pending`、`Authorized`、`Succeeded`、`Failed`、`Refunded`
- 账单：`Draft`、`Issued`、`PartiallyPaid`、`Paid`、`Overdue`、`Voided`

不负责：

- 修改账单明细
- 重新计算账单金额
- 改变订阅套餐

支付成功后，通过应用服务或进程内事件通知账单模块更新应收状态。

## 2. 依赖方向

推荐依赖关系：

```text
订阅 ─────┐
          ├──> 账单 ───> 支付
计量 ─────┘
```

约束：

- 订阅和计量不依赖支付
- 支付不直接依赖订阅
- 账单不能直接查询其他模块的表
- 每个模块只能通过本模块仓储访问本模块数据
- 公共代码仅放置值对象、错误码、时钟、ID生成器等基础能力，禁止放置业务逻辑

模块间调用使用明确的端口：

```text
Billing -> SubscriptionPort
Billing -> UsagePort
Payment -> ReceivablePort
```

实现可以位于同一进程，但接口必须保持模块隔离，便于测试和后续演进。

## 3. 数据与事务设计

### 数据隔离

可以使用同一个数据库实例，但按模块划分 schema 或表前缀：

```text
subscription_*
metering_*
billing_*
payment_*
```

数据库权限和代码检查共同保证禁止跨模块写表。跨模块读取必须通过查询接口或模块快照。

### 本地事务原则

一个业务不变式内的写操作使用一个本地数据库事务。例如：

- 创建订阅及其订阅项
- 写入用量原始记录并更新幂等表
- 生成账单及全部账单明细
- 记录支付回调并更新支付状态

事务边界放在应用服务层，不放在控制器或仓储层。

### 跨模块流程

跨模块流程采用最终一致性：

1. 订阅模块提交订阅变更事务。
2. 同一事务写入模块事件表。
3. 进程内发布器异步或同步分发事件。
4. 账单模块消费事件，生成待处理账单任务。
5. 任务执行时读取订阅快照和用量快照。
6. 账单生成后发布 `InvoiceIssued`。
7. 支付模块创建收款任务并执行支付。

虽然是单体，也建议使用事务消息表（Transactional Outbox），避免数据库提交成功但事件丢失。事件处理器必须幂等，并记录：

- `event_id`
- `consumer`
- `processed_at`
- `retry_count`
- `last_error`

### 账单生成事务

账单生成应保证：

- 同一订阅、同一账期只能有一个正式账单
- 使用唯一键：`subscription_id + period_start + period_end`
- 计算输入固定为快照
- 生成账单、明细、应收款和 `InvoiceIssued` 事件在同一事务内提交

并发生成时使用唯一约束或数据库锁，而不是依赖应用层判断。

### 支付回调事务

支付回调处理流程：

1. 以渠道事件 ID 去重。
2. 保存原始回调。
3. 校验支付订单、金额和币种。
4. 在一个事务中更新支付尝试和支付主状态。
5. 写入账单结算事件。
6. 提交后再执行通知、重试或外部副作用。

重复回调必须返回成功结果，但不得重复记账或重复退款。

## 4. 典型业务流程

### 新订阅

```text
创建订阅
 -> 校验套餐和价格
 -> 提交订阅事务
 -> 发布 SubscriptionActivated
 -> 创建首期账单
 -> 支付模块发起收款
 -> 支付成功
 -> 账单标记 Paid
```

### 周期计费

```text
关闭计费周期
 -> 计量模块冻结并生成用量快照
 -> 账单模块读取订阅快照和用量快照
 -> 计算账单明细
 -> 生成 Invoice
 -> 支付模块自动扣款
 -> 更新账单结算状态
```

### 订阅升级

明确变更策略：

- 立即升级：创建调整明细并按比例计算差额
- 周期末升级：只记录未来周期价格
- 降级：通常周期末生效，避免当前权益和金额不一致

所有变更保留历史，不能覆盖已经用于计费的旧价格。

## 5. 测试策略

### 单元测试

每个模块独立测试领域规则：

- 订阅状态转换和生效时间
- 计量幂等、单位换算和冲正
- 阶梯价格、折扣、税费、舍入
- 支付状态机和重复回调
- 账单逾期、部分支付和退款

金额计算使用固定精度 decimal，测试边界值、负数、极大值和舍入规则。

### 模块契约测试

验证模块公开接口和事件契约：

- 订阅查询返回完整价格快照
- 计量查询在账期关闭后结果稳定
- `InvoiceIssued` 字段版本兼容
- 支付只能结算存在且金额匹配的应收款

契约测试禁止绕过公开 API 直接操作其他模块表。

### 集成测试

使用真实数据库测试：

- 事务提交和回滚
- 唯一约束防重复账单
- Outbox 写入和事件发布
- 幂等记录与重复消息
- 并发账单生成
- 支付回调重放

### 端到端测试

覆盖关键用户旅程：

- 创建订阅到首笔支付
- 用量上报到周期账单
- 支付失败、重试、最终成功
- 部分支付、退款和账单结清
- 订阅变更后的下一期计费

### 属性与回归测试

对计费引擎加入属性测试，例如：

- 明细金额总和等于账单金额
- 同一输入重复计算结果一致
- 用量增加不会导致阶梯价格下降
- 账单生成具有幂等性

每个生产缺陷都补充为可重放的回归测试，并保存输入快照。

## 6. 运行与治理

- 一个应用、一个部署流水线、一个数据库集群即可。
- 模块拥有独立包目录、应用服务、领域模型、仓储和测试。
- 日志、指标按模块和业务 ID 关联。
- 监控重点包括账单生成延迟、未处理事件、支付失败率、对账差异和重复回调。
- 定期执行支付渠道、账单和应收款对账。
- 只有在团队规模、部署独立性或数据隔离需求真正出现时，才评估拆分；当前设计保持模块化单体，不预设微服务通信和运维成本。
