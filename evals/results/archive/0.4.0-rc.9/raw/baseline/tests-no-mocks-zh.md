## 测试目标

验证支付重试服务在真实依赖环境下能够：

- 成功完成支付并正确落库。
- 对瞬时失败按策略重试。
- 对永久失败立即终止。
- 正确执行指数退避、上限和抖动。
- 在重复请求、消息重投和并发场景下保持幂等。

全程不使用 mock。数据库、消息队列、缓存均运行真实实例；支付渠道使用官方 Sandbox。对于难以稳定触发的渠道错误，通过 Sandbox 提供的测试卡号、测试账户或错误码触发机制构造。

## 测试环境

- 与生产一致的服务构建和配置。
- 独立的 PostgreSQL/MySQL、Redis、消息队列实例。
- 支付渠道官方 Sandbox。
- 缩短但不改变算法的测试退避配置，例如 `100ms、200ms、400ms`。
- 每个用例使用唯一的 `payment_id`、订单号和幂等键。
- 采集数据库记录、队列消息、渠道交易记录、结构化日志和指标。
- 禁用测试进程自动重试，避免掩盖服务自身行为。

## 核心用例

| 场景 | 操作 | 预期结果 |
|---|---|---|
| 首次成功 | 提交一笔 Sandbox 可成功支付的请求 | 仅调用渠道一次；状态为 `SUCCEEDED`；重试次数为 0；金额、币种和渠道交易号正确 |
| 瞬时失败后成功 | 使用 Sandbox 的限流、超时或暂时不可用场景，使前两次失败后恢复 | 失败被判定为可重试；共尝试三次；最终 `SUCCEEDED`；只产生一笔渠道扣款 |
| 瞬时失败耗尽 | 持续触发可重试错误直到达到上限 | 尝试次数不超过配置；最终进入 `RETRY_EXHAUSTED` 或等价终态；不再产生后续任务 |
| 永久失败 | 使用余额不足、卡失效、参数非法等不可重试错误 | 仅尝试一次；状态为 `FAILED_PERMANENT`；无重试消息；失败原因被持久化 |
| 未知错误 | 触发未明确分类的渠道错误 | 按既定默认策略处理；不得无限重试；日志包含原始错误码和分类结果 |
| 退避 | 连续触发至少三次瞬时失败 | 相邻尝试时间符合配置的指数退避；达到最大间隔后不再增长 |
| 抖动 | 执行多批瞬时失败支付 | 延迟落在规定区间内，且任务没有集中在同一时间点；断言范围而非精确毫秒 |
| API 重复提交 | 使用相同幂等键重复提交相同请求 | 返回同一支付结果；只创建一条逻辑支付记录；渠道最多扣款一次 |
| 幂等键冲突 | 相同幂等键提交不同金额或订单 | 请求被拒绝并返回冲突；原支付记录不被修改 |
| 队列消息重复投递 | 将同一真实消息重复发布到队列 | 消息可被多次接收，但业务处理和渠道扣款最多一次 |
| 并发重复请求 | 多个线程或进程同时提交相同幂等键 | 仅一个请求获得执行权；其余返回同一结果或处理中状态；无重复扣款 |
| 消费中断恢复 | 渠道成功后、数据库确认前终止服务，再重启并重投消息 | 服务通过渠道幂等键或交易查询完成恢复；最终成功且没有二次扣款 |
| 重启期间退避 | 创建待重试任务后重启服务 | 下次执行时间保持不变；不会因重启立即重试或丢失任务 |
| 多实例竞争 | 启动多个真实服务实例消费同一任务 | 只有一个实例执行该次尝试；数据库状态和尝试计数一致 |

## 关键断言

退避时间不要按精确时间断言，应考虑调度和网络误差。例如无抖动时：

```text
实际间隔 ∈ [期望间隔 - 50ms, 期望间隔 + 150ms]
```

启用抖动时，根据实现验证其合法区间，例如：

```text
full jitter: 0 <= 实际间隔 <= 指数退避上限
equal jitter: 上限 / 2 <= 实际间隔 <= 上限
```

每个用例还应检查：

- `attempt_count` 与真实渠道请求数量一致。
- 状态转换只能向前，终态不能被旧消息覆盖。
- 金额、币种、订单号和幂等键在重试过程中不变。
- 每次尝试有唯一记录，并保留错误码、计划时间和实际时间。
- 终态后队列中不存在可继续执行的任务。
- 指标分别统计成功、可重试失败、永久失败、重试耗尽和幂等命中。

## 非 Mock 的故障构造

优先按以下顺序构造故障：

1. 使用支付渠道 Sandbox 官方错误场景。
2. 通过真实网络代理施加延迟、断连或连接重置。
3. 暂停或重启真实数据库、Redis、消息队列容器。
4. 对服务进程执行真实终止和重启。
5. 使用数据库锁或真实并发请求制造竞争。

网络故障工具属于测试基础设施，不返回伪造业务响应，因此不替代支付渠道本身。

## 通过标准

- 所有成功路径最终状态与 Sandbox 交易记录一致。
- 永久失败不发生重试。
- 瞬时失败严格受最大次数、最大持续时间和退避策略约束。
- 所有重复与并发场景中，单个逻辑支付最多产生一次真实扣款。
- 服务重启、消息重投和部分提交后仍能收敛到一致终态。
- 无无限重试、重复扣款、丢失任务或终态回退。
