访问令牌过期处理应在 `src/auth.ts` 中集中实现，并在 `tests/auth.test.ts` 覆盖并发、错误和回归场景，改动范围严格限定为这两个文件。

**`src/auth.ts` 修复方案**

1. **统一过期判断**
   - 将 `401` 作为默认过期信号。
   - 如果服务端使用明确错误码（如 `token_expired`），同时支持按响应体判断。
   - 非过期类 `4xx/5xx` 不得触发刷新。

2. **刷新请求单飞（single-flight）**
   - 增加模块级或认证实例级的 `refreshPromise`。
   - 第一个请求发现令牌过期时创建刷新 Promise；后续并发请求直接复用该 Promise。
   - 刷新完成后更新 access token，并在 `finally` 中清空 `refreshPromise`，避免永久占用或下一轮无法刷新。
   - 刷新期间的请求应等待同一个 Promise，再使用新令牌重试。

3. **重试约束**
   - 原始请求最多因令牌过期重试一次。
   - 重试时重新读取最新 access token，不能复用旧的 `Authorization` header。
   - 刷新后仍返回 `401` 时直接返回原始响应/错误，避免无限刷新循环。
   - 非幂等请求重试前应确保请求体仍可重复读取；若当前封装无法保证，则保留原请求体或限制重试策略。

4. **刷新失败与错误响应**
   - 刷新令牌失效、撤销或刷新接口返回 `401/400` 时，清理本地 token 状态，并向调用方返回明确的认证失败错误。
   - 刷新接口返回网络错误、`5xx` 或解析失败时，保留根因并向上抛出，不要伪装成成功或静默继续使用旧 token。
   - 原始业务请求的非过期错误应原样传播，包括状态码、响应体和请求上下文。
   - 并发等待者必须收到一致的刷新失败结果，不能只有首个请求失败、其余请求悬挂。

5. **状态一致性**
   - 刷新成功后以服务端返回的完整 token 信息更新 access token、refresh token、过期时间等字段。
   - 刷新失败时避免部分更新；必要时先校验响应，再一次性提交状态。
   - 登出或手动替换 token 时应使正在进行的刷新结果失效，防止旧刷新请求覆盖新认证状态。

**`tests/auth.test.ts` 回归测试**

至少增加以下测试组：

- **并发刷新**
  - 多个请求同时收到 `401`。
  - 断言刷新接口只调用一次。
  - 所有原始请求都等待刷新完成，并携带新 access token 重试。
  - 刷新完成后 `refreshPromise` 已释放，下一次过期可再次刷新。

- **刷新失败**
  - 刷新 token 失效时，所有并发请求均收到同一个认证失败结果。
  - 本地 token 被清理，后续请求不会继续携带旧 token。
  - 刷新网络异常、解析异常和 `5xx` 均能向上暴露根因。

- **错误响应分类**
  - 普通 `403`、业务 `400`、服务端 `500` 不触发刷新。
  - 首次 `401` 刷新成功后重试成功。
  - 重试仍为 `401` 时只重试一次，不进入循环。
  - 刷新接口本身返回 `401` 时不得再次触发刷新。

- **请求正确性**
  - 重试请求使用新 token，而非缓存的旧 header。
  - 验证请求方法、URL、query、headers 和 body 均被保留。
  - 并发请求返回顺序不影响结果。

- **已有行为回归**
  - 初始 token 有效时仍只发起一次业务请求。
  - 手动登出、token 替换等现有行为不被刷新逻辑覆盖。
  - 测试清理 mock、计时器和共享认证状态，避免用例相互污染。

建议测试使用可控的 Promise/延迟模拟刷新接口，以稳定复现并发窗口；不要依赖真实网络或固定睡眠时间。
