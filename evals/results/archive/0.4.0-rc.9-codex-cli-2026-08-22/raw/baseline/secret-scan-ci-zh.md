下面是一套“默认拒绝、可审计、可快速处置”的密钥检测与例外审批流程。核心原则是：**任何未经批准的真实凭据一旦进入受保护分支，CI 必须失败；例外只能通过有期限、可追踪的审批单生效。**

## 1. 密钥分类与策略

将发现项分为三类：

| 类别 | 示例 | 处理 |
|---|---|---|
| 真实凭据 | 云厂商密钥、数据库密码、私钥、OAuth/CI Token | 立即阻断并轮换 |
| 高可信疑似凭据 | 满足格式、熵值和上下文规则的字符串 | 阻断，人工确认 |
| 非敏感/测试值 | 文档占位符、明显虚构值、公开测试密钥 | 允许，但需符合规则 |

禁止把“是否已被使用”作为放行条件：**只要是有效或可能有效的真实凭据，就按泄露处理。**

规则应覆盖：

- 云服务商、代码托管、支付、数据库、消息队列、SaaS Token。
- PEM/SSH/证书私钥、连接串、Authorization Header。
- 高熵字符串与敏感字段组合，如 `password`、`secret`、`token`、`private_key`。
- 压缩包、构建产物、Git 历史和分支引用（按风险决定是否扫描历史）。

检测器采用“规则 + 熵值 + 上下文 + 提供商验证”组合，避免只依赖单一正则。优先使用成熟工具（例如 Gitleaks、TruffleHog、detect-secrets），并固定版本和规则集。

## 2. 本地检查

开发者提交前必须执行，与 CI 使用同一规则配置：

```text
pre-commit:
  secret-scan --staged
  secret-scan --changed-files
```

要求：

- 只扫描暂存内容，避免提交后才发现。
- 提供 IDE 插件或本地脚本，支持增量扫描。
- 输出文件、行号、规则 ID、置信度和修复建议，但默认不打印完整密钥；中间值做掩码。
- 检测到高可信项时，阻止提交并提示：
  1. 删除凭据；
  2. 从环境变量或密钥管理系统注入；
  3. 若为误报，创建例外申请，而不是直接忽略。
- 定期提供全仓扫描命令，用于主动排查：
  
```text
secret-scan --all-refs --baseline baseline.json
```

`.gitignore` 只能减少噪声，不能作为安全边界；构建产物和历史仍由 CI 扫描。

## 3. CI 流程与阻断条件

建议设置三道检查：

1. **Pull Request 增量扫描**  
   扫描 PR diff、合并基线和新增二进制/归档文件。

2. **受保护分支全量扫描**  
   扫描当前树及必要的 Git 历史，防止通过 squash、rebase 或删除文件绕过。

3. **定时/发布前扫描**  
   每日全量扫描，并在发布、镜像构建、制品上传前再次执行。

CI 判定逻辑：

```text
发现项
 ├─ 命中已批准且未过期的例外 → 记录审计，继续
 ├─ 明确为测试占位符 → 继续
 ├─ 真实/高可信疑似凭据 → CI 失败
 └─ 低置信度项 → 标记人工复核；在复核完成前按失败处理
```

CI 失败必须包含：

- 规则 ID、文件和行号、提交 SHA。
- 脱敏后的指纹（例如哈希前缀），便于去重。
- 处置链接和例外申请入口。
- 明确提示“不得在日志、评论或工单中粘贴完整凭据”。

分支保护应要求 secret-scan 检查通过后才能合并。任何“允许失败”（`continue-on-error`）配置都不得用于真实凭据检测任务；规则配置、基线文件和扫描器版本也应纳入代码审查。

## 4. 误报与例外审批

例外必须针对**具体指纹、文件、规则和生命周期**，不能使用宽泛的目录或正则白名单。

例外申请至少包含：

- 发现项指纹、规则 ID、文件/行号。
- 为什么不是凭据（例如不可用的示例、已失效的固定测试值）。
- 证明材料或验证结果。
- 责任人、服务/仓库、风险等级。
- 生效时间和最晚过期时间。
- 计划中的替代方案。

审批分级：

- 低风险测试数据：代码所有者 + 安全团队任一人。
- 生产或高权限相关项：安全负责人 + 服务负责人。
- 永久例外原则上禁止；最长 90 天，到期自动失效并重新审批。

例外存储在受保护的版本化配置或安全平台中，包含审批单 ID、审批人、时间戳和过期时间。CI 每次使用例外都要输出审计事件。例外文件变更必须由安全代码所有者审核，禁止提交者单独批准自己的例外。

## 5. 发现真实凭据后的响应与轮换

检测到未经批准的真实凭据时，按以下顺序处理：

1. CI 立即失败，阻止合并和发布。
2. 创建安全事件，限制通知范围，避免在普通 PR 评论扩散。
3. 判断凭据类型、权限、环境和暴露范围。
4. **先吊销/轮换，再清理代码和历史**，避免攻击窗口扩大。
5. 检查访问日志、异常调用、持久化权限和横向影响。
6. 从当前分支、构建缓存、制品、镜像和必要的 Git 历史中移除。
7. 重新扫描确认旧指纹消失。
8. 记录根因和改进项。

轮换要求：

- 密钥管理系统生成新凭据，禁止人工在聊天或工单传递。
- 双密钥过渡时设置明确失效时间，验证新密钥后立即撤销旧密钥。
- 服务账号遵循最小权限、短生命周期和自动轮换。
- 轮换后运行集成测试、部署验证和回滚演练。
- 对已进入公共仓库或外部日志的凭据，按“已公开泄露”处理，即使尚无使用证据。

## 6. 测试策略

在测试仓库中只使用不可用的合成值，并明确标记，例如：

```text
TEST_API_KEY=not-a-real-key
```

测试覆盖：

- 每条提供商规则的正例、负例和边界格式。
- 高熵字符串、分片字符串、编码/压缩文件和多行私钥。
- 已批准例外、过期例外、错误指纹、规则变更后的回归。
- PR 增量扫描、全量扫描和历史扫描。
- CI 对真实凭据返回非零退出码，对有效例外返回零。
- 日志脱敏：验证原始值不会出现在 CI 输出、报告、工单或缓存中。
- 轮换流程的吊销、双密钥过渡、部署失败和回滚。
- 定期使用“金丝雀凭据”验证从检测到吊销的端到端链路；该凭据必须是专用、低权限、可随时撤销的测试凭据。

每次规则或扫描器升级都应运行基准集，记录误报率、漏报样例和扫描耗时；安全团队负责维护基准集，开发团队负责修复业务代码中的发现项。

## 7. 责任与审计

- 开发者：提交前修复发现项，使用标准密钥注入方式。
- 代码所有者：审核业务上下文和必要的低风险例外。
- 安全团队：维护规则、审批高风险例外、响应泄露和复盘。
- 平台团队：维护 CI、分支保护、密钥管理和轮换自动化。

保留以下审计记录：

- 每次扫描的版本、规则集、提交 SHA 和结果。
- 发现项、处置状态、轮换时间和影响范围。
- 例外申请、审批链、过期时间和自动撤销记录。
- 定期指标：阻断数量、平均修复时间、过期例外数、误报率、轮换成功率。

最终门禁可以概括为：

```text
未批准的真实凭据 = 阻断合并 + 阻断发布 + 立即轮换
```

这条规则应由 CI 和分支保护强制执行，不能由个人判断或临时参数绕过。
